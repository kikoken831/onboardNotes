# Q61–Q90 — functional interfaces, more `CompletableFuture`, the queue family, `Executors`

---

### 61. What is the `java.util.function.Predicate` interface in Java, and how is it used?

<details><summary>Answer</summary>

`boolean test(T t)` — a boolean-valued question about one thing. The `filter` interface.

```java
Predicate<Trade> unsettled = t -> t.status() != SETTLED;
Predicate<Trade> large     = t -> t.notional().compareTo(THRESHOLD) > 0;
trades.stream().filter(unsettled.and(large)).toList();
```

Default methods make it composable: `and`, `or`, `negate`, plus statics `Predicate.not(p)` (JDK 11) and
`isEqual`. `Predicate.not(String::isBlank)` is the idiomatic way to avoid a clumsy lambda.

Primitive specialisations exist to dodge boxing: `IntPredicate`, `LongPredicate`, `DoublePredicate`. And
`BiPredicate<T,U>` for two arguments.

→ `quiz/17` Q3
</details>

### 62. What is the `java.util.function.Consumer` interface in Java, and how is it used?

<details><summary>Answer</summary>

`void accept(T t)` — a pure side effect. What `forEach` takes.

```java
trades.forEach(auditLog::record);
Consumer<Trade> pipeline = auditLog::record;
pipeline.andThen(metrics::count).accept(trade);      // chaining
```

Only one default method, `andThen`, because there's nothing to compose *out of* — a consumer returns
nothing.

Since a `Consumer` exists to mutate something, it's where side-effect discipline breaks down in stream
code: `stream().forEach(list::add)` on a parallel stream is a data race. Use `collect` instead.

`BiConsumer<T,U>` is what `Map.forEach` takes. Primitive versions: `IntConsumer` etc., plus
`ObjIntConsumer`.

→ `quiz/17` Q3, Q4
</details>

### 63. What is the `java.util.function.Supplier` interface in Java, and how is it used?

<details><summary>Answer</summary>

`T get()` — no input, one output. The point isn't the signature, it's that a `Supplier` is **deferred
computation**.

```java
value = optional.orElseGet(this::loadDefault);      // runs only if empty
log.debug(() -> expensiveDump());                   // built only if debug is on
```

That's why `orElseGet(supplier)` beats `orElse(loadDefault())`: the latter evaluates **eagerly, every
call**, even when the `Optional` is present. Same reason `CompletableFuture.supplyAsync` takes one, and
`ThreadLocal.withInitial` too.

There is deliberately **no `BiSupplier`** — zero inputs can't be doubled. Primitive versions:
`IntSupplier`, `BooleanSupplier`, etc.

→ `quiz/17` Q3, Q9
</details>

### 64. What is the `java.util.function.Function` interface in Java, and how is it used?

<details><summary>Answer</summary>

`R apply(T t)` — a transformation. What `map` takes, and the shape most of functional Java reduces to.

```java
Function<Trade, String> key = t -> t.book() + "|" + t.ccy();
key.andThen(String::toUpperCase);       // f then g
key.compose(Trade::normalise);          // g then f  -- note the order
Function.identity();                    // often needed by Collectors.toMap
```

`andThen` vs `compose` is the classic mix-up: `f.andThen(g)` is `g(f(x))`, `f.compose(g)` is `f(g(x))`.

Relations: `UnaryOperator<T>` **is** `Function<T,T>`; `BiFunction<T,U,R>` takes two (what `Map.merge` and
`thenCombine` take); `BinaryOperator<T>` is `BiFunction<T,T,T>` (what `reduce` takes). Primitive-flavoured
variants — `ToIntFunction`, `IntFunction`, `IntToLongFunction` — exist purely to avoid boxing.

→ `quiz/17` Q3, Q4
</details>

### 65. What is a `CompletableFuture.completeExceptionally()` method in Java, and how is it used?

<details><summary>Answer</summary>

Completes the future with a **failure**, from outside: `cf.completeExceptionally(new TimeoutException())`.
Returns `true` if this call was the one that transitioned it.

This is the *write* half — a `CompletableFuture` used this way is a **`Promise`**. It's how you bridge a
callback-based or message-driven API into the async world:

```java
var cf = new CompletableFuture<Ack>();
amps.subscribe(id, msg -> cf.complete(parse(msg)),
                   err -> cf.completeExceptionally(err));   // both paths must be wired
return cf.orTimeout(2, SECONDS);
```

The bug to avoid: wiring only the success path, so a failure leaves the future pending forever and the
caller hangs. `orTimeout` (JDK 9) is the safety net.

Downstream, the throwable arrives wrapped in `CompletionException` — unwrap with `getCause()` before
matching on type. Scala splits this cleanly into `Future` (read) and `Promise` (write), which is arguably
the better design.

→ `quiz/18` Q8; `quiz/12` Q8
</details>

### 66. What is a `CompletableFuture.cancel()` method in Java, and how is it used?

<details><summary>Answer</summary>

**It does not cancel anything.** `cancel(mayInterruptIfRunning)` completes the future with
`CancellationException` — and the boolean flag is **ignored**. The underlying computation keeps running
and keeps burning CPU.

That's the asymmetry that surprises people moving from `ExecutorService`: `FutureTask.cancel(true)` *does*
interrupt the worker thread. `CompletableFuture` has no handle on the thread doing the work, so it can't.

What to do instead when you need real cancellation:
- Keep the `Future` from `executor.submit(...)` and cancel **that**.
- Check `Thread.interrupted()` / a `volatile` flag inside long-running work.
- On JDK 21, use structured concurrency, where scope exit interrupts unfinished subtasks.

Note `isDone()` returns `true` for success, failure **and** cancellation — so it is not a success check.

→ `quiz/18` Q2, Q8
</details>

### 67. What is the difference between `Stream.forEach()` and `Stream.peek()` methods in Java?

<details><summary>Answer</summary>

`forEach` is a **terminal** operation and always runs. `peek` is an **intermediate** one and **may not
run at all** — twice over:

1. With **no terminal operation**, the whole pipeline never executes, so
   `list.stream().peek(print).filter(x -> x > 5);` prints nothing.
2. Even with a terminal op, `peek`'s action **may be skipped**: the Javadoc says it isn't invoked for
   elements whose production the implementation can optimise away, and `count()`'s own note says it may
   skip traversing the source entirely. So `list.stream().peek(print).count()` can print nothing on
   **JDK 9+** (this elision doesn't exist in 8u).

So `peek` is for **debugging only**. For a real side effect use `forEach`; to observe *and* keep the
stream, use `map(x -> { log(x); return x; })`, which cannot be elided.

One more: on a parallel stream `forEach` does **not** preserve encounter order — use `forEachOrdered` if
you need it. Don't over-claim the converse: the Javadoc's non-determinism statement is unqualified, so
just say "use `forEachOrdered` when order matters".

→ `quiz/17` Q7
</details>

### 68. What is a `java.util.concurrent.Exchanger` in Java, and how is it used?

<details><summary>Answer</summary>

A rendezvous where **exactly two threads swap objects**: each calls `exchange(myObject)` and receives the
other's.

```java
// producer                              // consumer
buf = exchanger.exchange(fullBuffer);    buf = exchanger.exchange(emptyBuffer);
```

The genuine use case is **buffer swapping** in a producer/consumer pair: the producer fills one buffer
while the consumer drains the other, and they trade at the boundary — no per-batch allocation, no queue.

Honest assessment: it's the rarest class in `java.util.concurrent`. Worth recognising, not worth reaching
for — a `BlockingQueue` of batches is clearer and nearly always fast enough. Effectively a
`CyclicBarrier(2)` that also carries data.

→ `quiz/18` Q20
</details>

### 69. What is the difference between `Runtime.getRuntime().availableProcessors()` and `java.util.concurrent.ForkJoinPool.getCommonPoolParallelism()` methods in Java?

<details><summary>Answer</summary>

`availableProcessors()` = CPUs the JVM believes it has. **Container-aware since JDK 10**, derived from the
cgroup **quota** — so a `cpu: 500m` limit reports **1**, and a *request* with no limit reports the full
host count.

`getCommonPoolParallelism()` = the common `ForkJoinPool`'s target parallelism, by default
**`availableProcessors() − 1`**, because the submitting thread also participates.

Measured on JDK 21.0.11, 14 cores: 14 and **13**. Two caveats from the same measurements:
- **The −1 is common-pool-only.** `new ForkJoinPool()` and `Executors.newWorkStealingPool()` both report
  the full **14**.
- **On 1 CPU the getter misleads you.** With `-XX:ActiveProcessorCount=1` the pool stops using workers
  and gives each task a **new thread** (`Thread-0`, `Thread-1`, …), yet
  `getCommonPoolParallelism()` still returns **1** because the getter floors it. So describe the
  *behaviour*, not the number — "it degrades to a thread per task while the metric still reads 1".

Override with `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N` or
`-XX:ActiveProcessorCount=N`.

→ `quiz/18` Q23; `quiz/04` Q12
</details>

### 70. What is the `Object.clone()` method in Java, and how is it used?

<details><summary>Answer</summary>

`protected native Object clone()` — a **field-for-field shallow copy** that bypasses constructors. To use
it the class must implement **`Cloneable`**, an **empty marker interface with no `clone()` method on it**;
without it, `clone()` throws `CloneNotSupportedException`.

Its problems, which are the actual answer:
- **Shallow** — nested mutable state is shared, so you must deep-copy by hand in an override.
- It **doesn't run a constructor**, so invariants and `final` field assignment are bypassed.
- The contract is convention, not enforcement: `x.clone() != x` and same-class are documented as
  "typically true", **not absolute requirements**.
- It interacts badly with `final` fields and inheritance.

**Use instead:** a **copy constructor** or a **static factory** (`new Order(other)`, `List.copyOf`,
`Order.from(other)`) — explicit, type-safe, works with `final` fields. Josh Bloch, who wrote `Cloneable`,
recommends against it. Best of all, design the type **immutable** and you never need a copy.

→ `quiz/16` Q11
</details>

### 71. What is the `java.util.Optional` class in Java, and how is it used?

<details><summary>Answer</summary>

A container for "a value that may legitimately be absent", designed as a **return type** so callers can't
ignore the absent case as easily as they ignore `null`.

```java
repo.findTrade(id)
    .map(Trade::notional)
    .filter(n -> n.signum() > 0)
    .orElseThrow(() -> new NotFoundException(id));
```

Correct use: chain with `map`/`flatMap`/`filter`, terminate with
`orElse`/`orElseGet`/`orElseThrow`/`ifPresent`. Never `if (o.isPresent()) return o.get();` — that's the
null check you were escaping, with more syntax.

Facts worth having exactly right:
- **`get()` is not deprecated** — it's discouraged by an `@apiNote` pointing at `orElseThrow()` (no-arg
  form since JDK 10). Call it soft-deprecated, not deprecated.
- **`Optional` is not `Serializable`**, which is one reason not to use it as a field.
- The "don't use it as a field or parameter" rule is **JDK-team commentary, not documentation** —
  attribute it that way. An `Optional` parameter gives callers three states, which is worse than two.
- `orElse(expensive())` evaluates **eagerly**; use `orElseGet`.
- Never wrap a collection — return an empty collection instead.

→ `quiz/17` Q9, Q10
</details>

### 72. What is a `CompletableFuture.complete()` method in Java, and how is it used?

<details><summary>Answer</summary>

Completes the future **successfully** with a value you supply, from outside the computation:
`cf.complete(ack)`. Returns `true` if this call was the transition — so it's also a race-winner test,
which is how you implement "first response wins" over several sources.

Paired with `completeExceptionally`, this is the `Promise` half of the class, and the reason
`CompletableFuture` can adapt any callback API:

```java
var cf = new CompletableFuture<Quote>();
client.onQuote(cf::complete);
client.onError(cf::completeExceptionally);
```

Related: `getNow(fallback)` reads without blocking; `obtrudeValue` forcibly overwrites an
already-completed result (a debugging tool — don't ship it); and `completeAsync`/`completeOnTimeout`
(JDK 9) cover the common "default after N ms" case without a manual timer.

→ `quiz/18` Q8
</details>

### 73. What is the `Stream.collect()` method in Java, and how is it used?

<details><summary>Answer</summary>

The terminal **mutable reduction**: supplier creates a container, accumulator folds each element in,
combiner merges containers in parallel.

```java
Map<String, BigDecimal> byCcy = trades.stream()
    .collect(groupingBy(Trade::ccy, reducing(ZERO, Trade::notional, BigDecimal::add)));
```

The contrast with `reduce` is the point: `reduce` is *immutable* reduction, so `reduce("", String::concat)`
is O(n²) while `collect(joining())` is O(n).

Two gotchas: **`Collectors.toMap` throws `IllegalStateException` on a duplicate key** — pass a merge
function — and it **NPEs on a null value** (from a `requireNonNull` in the accumulator; only
`toUnmodifiableMap` documents the prohibition, and null *keys* are accepted). Assert the exception
**type**, never the message: `toMap`'s message text changed in JDK 9.

Also `stream.toList()` (JDK 16) is shorter than `collect(toList())` and returns an **unmodifiable** list;
`collect(toList())` returns a mutable `ArrayList`.

→ `quiz/17` Q12
</details>

### 74. What is a `CompletableFuture.runAsync()` method in Java, and how is it used?

<details><summary>Answer</summary>

Runs a **`Runnable`** asynchronously → `CompletableFuture<Void>`. The side-effecting sibling of
`supplyAsync`, which takes a `Supplier` and yields a value.

```java
runAsync(() -> auditLog.flush(), ioExecutor)
    .exceptionally(ex -> { log.error("flush failed", ex); return null; });
```

Same executor rule: the one-arg form uses the shared common `ForkJoinPool`, so **pass your own executor
for anything that blocks**.

The `Void` result is a trap: with nothing to consume, it's easy to fire-and-forget and never observe
completion — and **an exception in an unobserved `CompletableFuture` is silently swallowed**, unlike a
raw thread's uncaught exception. Always attach `exceptionally` or `whenComplete` to a `runAsync` you don't
join.

→ `quiz/18` Q3
</details>

### 75. What is the `java.util.function.BiPredicate` interface in Java, and how is it used?

<details><summary>Answer</summary>

`boolean test(T t, U u)` — a two-argument predicate. Composable with `and`/`or`/`negate`, same as
`Predicate`.

```java
BiPredicate<Trade, Ssi> deliverable = (t, s) -> s.supports(t.ccy()) && s.active();
```

Where it actually shows up: as an argument to APIs that iterate pairs, and as a matcher in
reconciliation-style code — "does this internal record correspond to this external one?" — which is a
real post-trade shape. In practice, most two-argument predicates read better as a method on a small
record.

The `Bi-` family: `BiPredicate<T,U>`, `BiConsumer<T,U>` (what `Map.forEach` takes),
`BiFunction<T,U,R>` (what `Map.merge` and `thenCombine` take). There's **no `BiSupplier`** (nothing to
double) and **no `TriFunction`** — past two parameters the JDK expects a record, which is usually the
better design anyway.

→ `quiz/17` Q4
</details>

### 76. What is a `CompletableFuture.thenRun()` method in Java, and how is it used?

<details><summary>Answer</summary>

`thenRun(Runnable)` — runs an action after completion, **ignoring the result** → `CompletableFuture<Void>`.
Use it when the next step doesn't care what the value was: releasing a permit, clearing a cache, emitting
a metric.

The trio by argument type: `thenApply(Function)` uses the value and returns one;
`thenAccept(Consumer)` uses the value and returns nothing; **`thenRun(Runnable)` uses nothing and returns
nothing**.

The important limitation: `thenRun` **doesn't run on failure**. If the upstream stage completes
exceptionally, the whole chain short-circuits and your "cleanup" never happens. For `finally` semantics
use **`whenComplete`**, which always runs and sees both outcomes while leaving the result unchanged.

```java
f.whenComplete((v, ex) -> sem.release());     // right
f.thenRun(sem::release);                      // leaks a permit on failure
```

→ `quiz/18` Q4, Q6
</details>

### 77. What is a `CompletableFuture.exceptionally()` method in Java, and how is it used?

<details><summary>Answer</summary>

`exceptionally(Function<Throwable, T>)` — the **recovery** path: it runs only on failure and supplies a
fallback value of the same type.

```java
loadRate(ccy).exceptionally(ex -> { metrics.count("rate.fallback"); return cachedRate(ccy); });
```

The family, and how to choose:

| Method | Runs on | Can change the value? | Consumes the exception? |
|---|---|---|---|
| `exceptionally` | failure only | yes (supplies fallback) | **yes** |
| `handle` | always | yes, **and the type** | **yes** |
| `whenComplete` | always | no | **no** — it propagates |

So `whenComplete` is `finally`; `exceptionally` is `catch`; `handle` is both plus a transform.

Two details: the throwable is usually wrapped in **`CompletionException`**, so unwrap with `getCause()`
before matching on type; and `exceptionallyCompose` (JDK 12) is the version for when your fallback is
itself async.

→ `quiz/18` Q6
</details>

### 78. What is the `java.util.function.BiConsumer` interface in Java, and how is it used?

<details><summary>Answer</summary>

`void accept(T t, U u)` — a two-argument side effect. Most visibly, it's what **`Map.forEach`** takes:

```java
positions.forEach((book, qty) -> log.info("{} = {}", book, qty));
```

Also what `CompletableFuture.whenComplete(BiConsumer<T, Throwable>)` takes — which is a nice illustration
of the pattern "value **and** error, observe both, change neither".

`andThen` is its only default method. Primitive variants are the odd-looking `ObjIntConsumer<T>`,
`ObjLongConsumer<T>`, `ObjDoubleConsumer<T>`.

Same caution as `Consumer`: it exists to mutate something, so in stream code it's where thread-safety
goes wrong. `Map.forEach` on a `ConcurrentHashMap` is safe to *read* but gives you no atomicity across
entries.

→ `quiz/17` Q4
</details>

### 79. What is a `CompletableFuture.thenCombine()` method in Java, and how is it used?

<details><summary>Answer</summary>

Combines **two** futures that run independently, with both values typed:

```java
CompletableFuture<Settlement> s = loadTrade(id)
    .thenCombine(loadSsi(id), (trade, ssi) -> new Settlement(trade, ssi));
```

`thenCombine(other, BiFunction<T,U,V>)` waits for both and applies the function. This is the **type-safe
choice whenever the fan-out is fixed and small** — much better than `allOf`, which returns
`CompletableFuture<Void>` and makes you re-read the inputs, and better than `anyOf`, which is untyped.

Note both futures must already have been *started* — `thenCombine` doesn't start anything, it composes.
So build them eagerly (`supplyAsync`) and let them overlap; if you accidentally construct the second
inside a `thenCompose` you've serialised them.

`thenAcceptBoth` is the same shape with a `BiConsumer` and no result; `runAfterBoth` ignores both values.

→ `quiz/18` Q7
</details>

### 80. What is a `CompletableFuture.thenAcceptBoth()` method in Java, and how is it used?

<details><summary>Answer</summary>

`thenAcceptBoth(other, BiConsumer<T,U>)` — waits for both futures, consumes both values, returns
`CompletableFuture<Void>`. The side-effecting version of `thenCombine`.

```java
loadTrade(id).thenAcceptBoth(loadSsi(id), (t, s) -> audit.record(t, s));
```

The full two-future set, by what they do with the values: **`thenCombine`** → returns a new value;
**`thenAcceptBoth`** → consumes both; **`runAfterBoth`** → ignores both. And the "either" mirrors:
`applyToEither`, `acceptEither`, `runAfterEither` — which are the *typed* two-future alternative to
`anyOf`, and generally what you actually want instead of it.

Same failure semantics as the rest of the family: if either input fails, the combined stage fails and the
action doesn't run — so cleanup belongs in `whenComplete`, not here.

→ `quiz/18` Q7
</details>

### 81. What is the `java.lang.invoke.MethodHandle` class in Java, and how is it used?

<details><summary>Answer</summary>

A typed, directly-executable reference to a method, field or constructor — obtained from a
`MethodHandles.Lookup` and invoked with `invokeExact` or `invoke`.

```java
var mh = MethodHandles.lookup()
    .findVirtual(Trade.class, "notional", MethodType.methodType(BigDecimal.class));
BigDecimal n = (BigDecimal) mh.invokeExact(trade);
```

**The documented difference from core reflection is access checking:** the check happens **once, when the
`Lookup` creates the handle**, whereas `Method.invoke` re-checks against the caller on **every**
invocation. (That's the spec-level claim; treat "it's faster" as a consequence, not a documented
guarantee — though a `static final` handle is designed to be JIT-inlinable.)

`invokeExact` requires the symbolic type descriptor to match **exactly**; `invoke` permits `asType`
adaptations (boxing, widening, casts).

Why it exists: to support **`invokedynamic`**, which underpins **lambdas** (`LambdaMetafactory`), string
concatenation since JDK 9, and records. Sibling worth naming: **`VarHandle`** (JDK 9) for field and array
access with explicit memory-ordering modes — the supported replacement for `sun.misc.Unsafe`.

→ `quiz/16` Q17
</details>

### 82. What is a `java.util.concurrent.ConcurrentSkipListMap` in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q30 compared it with `TreeMap` — this angle is the API you'd actually use.)*

It implements **`ConcurrentNavigableMap`**, so beyond `Map` you get the ordered operations, all safe
under concurrent modification:

```java
book.headMap(limitPrice, true);          // everything at or better than a price
book.firstEntry(); book.pollFirstEntry(); // best bid/offer, atomically removed
book.ceilingKey(px); book.floorKey(px);   // nearest tradable level
book.descendingMap();                     // reverse view, no copy
book.subMap(from, true, to, false);       // range view
```

`pollFirstEntry`/`pollLastEntry` are the atomically-remove-the-extreme operations — that's what makes it
usable as a concurrent priority structure with **ordered range access**, which `PriorityBlockingQueue`
can't give you.

Two practical notes: the views are **live** and write through, and **`size()` is O(n)** because it walks
the list. `ConcurrentSkipListSet` is the same structure as a `Set`.

→ `quiz/18` Q17
</details>

### 83. What is a `java.util.concurrent.PriorityBlockingQueue` in Java, and how is it used?

<details><summary>Answer</summary>

An **unbounded** blocking queue ordered by natural order or a `Comparator` — a concurrent priority queue.

```java
var q = new PriorityBlockingQueue<Instruction>(64, comparing(Instruction::deadline));
```

Two things to say, because both are surprising:
1. **Unbounded**, so it cannot apply backpressure. `put` never blocks; under overload it grows until you
   OOM. Same memory-sink risk as `LinkedBlockingQueue`'s unbounded default.
2. **The iterator does not traverse in priority order** — only `poll`/`take` respect ordering. Neither
   does `toString`, or draining via `stream()`. This trips people writing tests.

`take()` blocks only when the queue is **empty**, unlike `DelayQueue` where the head may exist but not
yet be available.

Elements must be mutually comparable, and mutating a queued element's ordering field corrupts the heap
invariant.

→ `quiz/18` Q21
</details>

### 84. What is the `java.util.concurrent.TransferQueue` interface in Java, and how is it used?

<details><summary>Answer</summary>

A `BlockingQueue` that adds **producer-side waiting for a consumer**:

- `transfer(e)` — block until a consumer **receives** the element (not merely until it's enqueued).
- `tryTransfer(e)` — hand off only if a consumer is already waiting, else return `false` immediately.
- `tryTransfer(e, timeout, unit)`, `hasWaitingConsumer()`, `getWaitingConsumerCount()`.

The distinction from `put` is the whole point: `put` returns as soon as the element is *queued*, so the
producer learns nothing about progress. `transfer` gives you genuine **handoff** semantics, which is what
you want for request/response over a queue, or to keep a work item from sitting unclaimed.

Think of it as spanning the gap between `LinkedBlockingQueue` (always buffer) and `SynchronousQueue`
(never buffer): a `TransferQueue` can do either, per operation.

The JDK's only implementation is `LinkedTransferQueue`.

→ `quiz/18` Q16
</details>

### 85. What is a `java.util.concurrent.SynchronousQueue` in Java, and how is it used?

<details><summary>Answer</summary>

A queue with **zero capacity**. Every `put` blocks until a `take` arrives and vice versa — a direct
handoff, never a buffer. `isEmpty()` is always `true`, `size()` always `0`, `peek()` always `null`.

Where you meet it: **`Executors.newCachedThreadPool()` uses it.** Because the queue always "rejects" an
offer with no waiting consumer, the pool's admission algorithm falls through to creating a thread — which
is exactly how a cached pool grows to one thread per concurrent task (and why it can OOM on thread stacks,
with `maximumPoolSize` = `Integer.MAX_VALUE`).

Use it directly when you want a strict rendezvous with no queueing: the producer must not run ahead of the
consumer at all. Optionally **fair** (FIFO) via the constructor.

→ `quiz/18` Q16; `quiz/02` Q2
</details>

### 86. What is the `java.util.concurrent.LinkedTransferQueue` in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q84 covered the interface — this angle is the implementation and when to pick it.)*

The **only** `TransferQueue` implementation: unbounded, linked, and internally a "dual queue" that holds
either waiting elements or waiting consumers, matched by CAS with no locks on the fast path.

Why choose it over the alternatives:
- vs **`LinkedBlockingQueue`** — no head/tail locks at all, and it can do handoff via `transfer`. It
  generally benchmarks faster under contention. It is, however, **strictly unbounded** — `LBQ` at least
  *offers* a capacity, so if you need backpressure `LinkedTransferQueue` is the wrong choice.
- vs **`SynchronousQueue`** — it can buffer when you want to (`put`) and rendezvous when you want to
  (`transfer`), rather than being fixed at zero capacity.

`take()` on an empty queue spins briefly before parking, which is why it does well when producers and
consumers are roughly balanced.

→ `quiz/18` Q16
</details>

### 87. What is a `java.util.concurrent.LinkedBlockingDeque` in Java, and how is it used?

<details><summary>Answer</summary>

A **blocking, optionally bounded** double-ended queue — `BlockingDeque` implemented over a linked list
with a single lock.

```java
var dq = new LinkedBlockingDeque<Task>(1000);      // bound it
dq.putFirst(urgent); dq.putLast(normal);
Task t = dq.takeFirst();                            // blocks
```

Every operation comes in a First/Last pair, in the three failure styles: `putX`/`takeX` block,
`offerX`/`pollX` return a boolean/null (optionally with timeout), `addX`/`removeX` throw.

When it's the right answer: **work stealing** (own end LIFO for locality, other end FIFO for stealers),
and a **priority-lite** scheme where "urgent" goes to the front without a comparator. Also usable as a
bounded LIFO stack, which `ArrayBlockingQueue` can't be.

Cost: one lock for both ends, so it doesn't scale like `LinkedBlockingQueue`'s two-lock design under heavy
symmetric load.

→ `quiz/18` Q18
</details>

### 88. What is the `java.lang.ThreadLocal` class in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q17 covered the hazards — this angle is the class's mechanics and its modern replacement.)*

The storage lives **on the `Thread`**, not in the `ThreadLocal` object: each thread carries a
`ThreadLocalMap` whose **key is a weak reference to the `ThreadLocal`** and whose **value is strong**.
That asymmetry is the whole reason unremoved entries leak on pooled threads — exactly the `WeakHashMap`
shape.

API: `get()`, `set(v)`, `remove()`, and `withInitial(Supplier)` (JDK 8) in preference to subclassing
`initialValue()`.

**`ScopedValue`** (JDK 21+, still a **preview** API as of August 2026) is the modern replacement, and it
fixes the design rather than the symptom:

```java
ScopedValue.where(CONTEXT, ctx).run(() -> handle(request));   // unbound automatically at block exit
```

Immutable, explicitly scoped, no `finally` needed, no leak possible, and cheap to inherit across
structured-concurrency forks. It exists largely because `ThreadLocal` scales badly to millions of virtual
threads — a per-thread map per virtual thread is a lot of maps.

→ `quiz/18` Q24; `quiz/03` Q8
</details>

### 89. What is the `java.util.concurrent.Executors.newCachedThreadPool()` method in Java, and how is it used?

<details><summary>Answer</summary>

`ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, SECONDS, new SynchronousQueue<>())`.

So: no core threads, **unbounded maximum**, threads idle for 60 s are reaped, and a **zero-capacity
queue** — which is what forces a new thread for every task that finds no idle worker.

Suits short-lived, bursty, **non-blocking** tasks where the burst is naturally bounded.

**The failure mode is unbounded threads.** Under sustained load it will happily create tens of thousands
and die on thread stacks (`OutOfMemoryError: unable to create native thread`) — the mirror image of
`newFixedThreadPool`'s unbounded *queue*. Neither applies backpressure; both just fail differently.

Prefer an explicit `ThreadPoolExecutor` with a bounded queue and a deliberate rejection policy. On JDK 21,
`newVirtualThreadPerTaskExecutor()` is the honest version of what people wanted from a cached pool — one
thread per task, but the threads are nearly free.

→ `quiz/18` Q22; `quiz/02` Q2
</details>

### 90. What is the `java.util.concurrent.Executors.newFixedThreadPool()` method in Java, and how is it used?

<details><summary>Answer</summary>

`ThreadPoolExecutor(n, n, 0L, MILLISECONDS, new LinkedBlockingQueue<>())` — n threads always, and an
**unbounded queue**.

That queue is the problem, and it's the whole reason this factory is on every "don't use" list. Because
the queue never rejects, the admission algorithm's step 3 (grow to max) **never happens** — and since
core == max here, that's moot, but the real cost is memory: tasks accumulate without limit until the JVM
OOMs. Measured in `problems/java/P05`: the queue reached 100,000 entries while the pool stayed at core
size.

No backpressure means the submitter never learns it's overproducing. The fix is a **bounded** queue plus
`CallerRunsPolicy`, which throttles the submitter naturally:

```java
new ThreadPoolExecutor(n, n, 0L, MILLISECONDS,
    new ArrayBlockingQueue<>(1000), namedFactory, new CallerRunsPolicy());
```

Also worth knowing: `newFixedThreadPool(1)` **can** be cast to `ThreadPoolExecutor` and reconfigured,
whereas `newSingleThreadExecutor()` is wrapped so it can't (measured: `instanceof` → `true` vs `false`).

→ `quiz/18` Q22; `quiz/02` Q2, Q3
</details>
