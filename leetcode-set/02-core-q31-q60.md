# Q31–Q60 — locks, synchronisers, `CompletableFuture` methods, concurrent collections

---

### 31. What is the difference between `Thread.sleep()` and `Object.wait()` methods in Java?

<details><summary>Answer</summary>

**`sleep()` does not release any lock. `wait()` releases the monitor it's waiting on.** That's the whole
answer, and getting it wrong is how you write a deadlock.

- `Thread.sleep(ms)` — static, no lock involvement, wakes on time or interruption.
- `obj.wait()` — must be called **holding `obj`'s monitor**; releases it, parks, and re-acquires before
  returning. Wakes on `notify`/`notifyAll`, interruption, timeout, or **spuriously** — so it must always
  be in a loop re-checking the condition:

```java
synchronized (queue) {
    while (queue.isEmpty()) queue.wait();   // while, never if
    return queue.poll();
}
```

Calling `wait()` without the monitor throws `IllegalMonitorStateException`. Prefer `notifyAll` to
`notify` (a single `notify` can wake the wrong waiter and stall). Modern code should use
`BlockingQueue` or `Condition` instead of either.

Also: a `notify` with no one waiting is **lost** — unlike `LockSupport.unpark`, which is remembered.

→ `quiz/01` Q6, Q7
</details>

### 32. What is the difference between `Comparator` and `Comparable` interfaces in Java?

<details><summary>Answer</summary>

**`Comparable<T>.compareTo(T)`** is the type's **natural order**, implemented *on* the class — one
ordering, and it's what `TreeMap`/`TreeSet`/`Arrays.sort` use by default.

**`Comparator<T>.compare(a, b)`** is an **external** ordering — as many as you like, and you can order
types you don't own.

Rules of thumb: implement `Comparable` when there's one obvious order (`BigDecimal`, `LocalDate`); use
`Comparator` for everything else. Keep `compareTo` **consistent with `equals`**, because `TreeSet`
dedupes by `compareTo == 0`, not by `equals` — an inconsistent pair silently drops elements.

→ `quiz/17` Q16; `quiz/09` Q5
</details>

### 33. What is a `Phaser` class in Java, and how is it used?

<details><summary>Answer</summary>

A reusable barrier with a **dynamic** party count and numbered **phases** — strictly more capable than
`CountDownLatch` and `CyclicBarrier` together.

```java
var phaser = new Phaser(1);                       // register self
for (var task : tasks) {
    phaser.register();                            // parties can join at runtime
    pool.submit(() -> { work(task); phaser.arriveAndDeregister(); });
}
phaser.arriveAndAwaitAdvance();
```

Key API: `register`/`bulkRegister`, `arrive`, `arriveAndAwaitAdvance`, `arriveAndDeregister`,
`getPhase()` (monotonically increasing), and `onAdvance(phase, parties)` — override it to control
termination. It supports **tiering** (a parent phaser) to cut contention across many parties.

Use it when the number of participants changes at runtime; otherwise its extra flexibility is just extra
ways to be wrong.

→ `quiz/18` Q10
</details>

### 34. What is a `StampedLock` in Java, and how is it used?

<details><summary>Answer</summary>

A JDK 8 lock with three modes — write, read, and **optimistic read**, which takes no lock at all:

```java
long stamp = lock.tryOptimisticRead();
double x = this.x, y = this.y;            // read into locals
if (!lock.validate(stamp)) {              // a writer intervened?
    stamp = lock.readLock();
    try { x = this.x; y = this.y; } finally { lock.unlockRead(stamp); }
}
```

Much faster than `ReentrantReadWriteLock` for read-heavy state because the common path is two volatile
reads and no bookkeeping.

The costs, which are real: it is **not reentrant** (re-acquiring deadlocks), you must carry the
**stamp** to unlock, it doesn't support `Condition`, and it supports **explicit conversion**
(`tryConvertToWriteLock`) rather than the illegal upgrade. Also: optimistic reads must copy into locals
before validating, or you may act on a torn read.

→ `quiz/18` Q11
</details>

### 35. What is a `LockSupport` class in Java, and how is it used?

<details><summary>Answer</summary>

The low-level parking primitive: `LockSupport.park()` blocks the current thread,
`LockSupport.unpark(thread)` makes a specific thread runnable.

The property that makes it usable where `wait`/`notify` isn't: it holds a **single binary permit**, and
**`unpark` before `park` is remembered** — so the permit makes the subsequent `park()` return
immediately. A `notify` before a `wait` is lost.

Two more: `park()` may return **spuriously** at any time, so always re-check your condition in a loop;
and it responds to interruption by returning **without throwing and without clearing** the flag.

You'd rarely call it directly. It matters because **`AbstractQueuedSynchronizer`** is built on it — a
`volatile int state` plus a CAS wait queue plus `park`/`unpark` — and AQS is what `ReentrantLock`,
`Semaphore`, `CountDownLatch` and `FutureTask` are made of. That's the answer to "how does
`ReentrantLock` actually work?"

→ `quiz/18` Q12
</details>

### 36. What is a `CompletableFuture.supplyAsync()` method in Java, and how is it used?

<details><summary>Answer</summary>

Starts async work that **produces a value**: `supplyAsync(Supplier<U>)` →
`CompletableFuture<U>`.

```java
CompletableFuture<Trade> f = supplyAsync(() -> repo.load(id), ioExecutor);
```

**Always pass your own executor for blocking work.** The one-arg form uses
`ForkJoinPool.commonPool()`, which is shared with every `parallelStream()` in the JVM and sized to
`cores − 1`. One blocking JDBC call there starves unrelated code.

Measured edge case on JDK 21.0.11 with `-XX:ActiveProcessorCount=1`: the common pool stops using workers
and hands each task a **brand-new thread** (`Thread-0`, `Thread-1`, …) — while
`getCommonPoolParallelism()` still reports 1, so metrics hide it.

An exception thrown inside the supplier completes the future exceptionally rather than propagating.

→ `quiz/18` Q3
</details>

### 37. What is the difference between `Stream.filter()` and `Stream.map()` methods in Java?

<details><summary>Answer</summary>

`filter(Predicate<T>)` → `Stream<T>`: **same type**, 0..n elements out of n.
`map(Function<T,R>)` → `Stream<R>`: **possibly new type**, exactly n out of n.

`flatMap` is the third and the one worth being able to explain: it maps each element to a **stream** and
concatenates, so it's the only one that changes both type and count — flattening `List<Order>` into all
their items, or `Stream<Optional<T>>` into `Stream<T>`.

Both are **lazy** intermediate operations: nothing runs until a terminal operation, and then each element
flows through the whole chain once (fusion), with short-circuiting where possible.

→ `quiz/17` Q6, Q8
</details>

### 38. What is a `CompletableFuture.thenApply()` method in Java, and how is it used?

<details><summary>Answer</summary>

`thenApply(Function<T,U>)` transforms the result — the `map` of `CompletableFuture`:
`f.thenApply(Trade::notional)`.

**The important part is which thread runs it.** Without the `Async` suffix the callback runs on
**whichever thread completes the stage** — or, if the stage is already complete when you attach it, on the
**calling thread, synchronously**. So a slow non-`Async` callback can hijack a Netty I/O thread, and the
non-determinism makes it hard to test.

Rule: if the callback is non-trivial, use `thenApplyAsync(fn, myExecutor)`.

Siblings: `thenAccept` (consume, no result), `thenRun` (ignore the value), and **`thenCompose`** when
your function itself returns a `CompletableFuture` — `thenApply` would nest it.

→ `quiz/18` Q4
</details>

### 39. What is a `CompletableFuture.join()` method in Java, and how is it used?

<details><summary>Answer</summary>

Blocks and returns the result, throwing the **unchecked** `CompletionException` on failure.

The contrast with `get()` is the whole point: `get()` throws **checked** `ExecutionException` and
`InterruptedException`. So `join()` is usable inside a lambda and `get()` isn't:

```java
allOf(futures).thenApply(v -> Arrays.stream(futures).map(CompletableFuture::join).toList());
```

That's safe because `allOf` has already guaranteed completion. Calling `join()` on a pending future in
request-handling code is how you turn an async pipeline back into a blocking one — and if you do it on a
common-pool thread, you can deadlock the pool.

Unwrap the cause before matching on type: the throwable is wrapped in `CompletionException`.

→ `quiz/18` Q8
</details>

### 40. What is a `CountDownLatch` in Java, and how is it used?

<details><summary>Answer</summary>

"Wait for **n events**." `new CountDownLatch(n)`, workers call `countDown()`, waiters call `await()`
until the count reaches zero.

```java
var ready = new CountDownLatch(1);          // starting gun
var done  = new CountDownLatch(threads);    // finish line
```

That two-latch pattern is the standard way to write a concurrency test — it's what
`problems/java/P01`–`P09` use to maximise the chance of an interleaving showing up.

**One-shot**: once it hits zero it stays there, and there is **no reset**. It's also asymmetric —
counters and waiters are different threads — which is what distinguishes it from `CyclicBarrier`.

Use `await(timeout, unit)` in production so a lost `countDown` doesn't hang you forever.

→ `quiz/18` Q9
</details>

### 41. What is a `CyclicBarrier` in Java, and how is it used?

<details><summary>Answer</summary>

"Wait for **n threads** to arrive." Symmetric — every party calls `await()` — and it **re-arms
automatically** after each trip, which is why it suits round-based simulations.

`new CyclicBarrier(n, barrierAction)` runs the action on the **last-arriving thread** before any party is
released.

The fragile part: interruption, timeout, or a throwing barrier action puts it in a **broken** state, and
every current and future waiter then gets `BrokenBarrierException` until someone calls `reset()`. That
all-or-nothing failure mode is why production code usually prefers a `Phaser` or a latch per round.

→ `quiz/18` Q9, Q10
</details>

### 42. What is the `ClassLoader.defineClass()` method in Java, and how is it used?

<details><summary>Answer</summary>

It turns a `byte[]` of class-file bytes into a `Class` object. All four overloads are **`protected
final`**, so you can only call it from inside a `ClassLoader` subclass — which is exactly how custom
loaders, app servers and instrumentation frameworks load generated or transformed bytecode.

The modern, public alternatives:
- **`MethodHandles.Lookup.defineClass(byte[])`** (`@since 9`) — public, requires **PACKAGE** lookup
  mode, defines the class with the **same loader, package and protection domain** as the lookup class,
  and links it **without running the static initialiser**.
- **`Lookup.defineHiddenClass(bytes, initialize, options)`** (`@since 15`) — needs full privilege
  access and produces a class with **no binary name**, undiscoverable by `Class.forName` /
  `loadClass` / `findClass` and unmodifiable by agents. It's what lambdas and other JDK internals use.

Related: `ClassNotFoundException` (checked, reflective load failed) vs `NoClassDefFoundError` (present at
compile time, missing or failed initialisation at runtime).

→ `quiz/16` Q15
</details>

### 43. What is a `ReentrantReadWriteLock` in Java, and how is it used?

<details><summary>Answer</summary>

Two paired locks: readers share, a writer excludes everyone.

```java
var lock = new ReentrantReadWriteLock();
lock.readLock().lock();  try { … } finally { lock.readLock().unlock(); }
lock.writeLock().lock(); try { … } finally { lock.writeLock().unlock(); }
```

**The asymmetry to know cold: upgrade is not supported and deadlocks** — acquiring the write lock while
holding the read lock makes the thread wait for itself. **Downgrade works**: take the read lock while
holding write, then release write. That's the documented idiom.

Also: the default is **unfair**, which permits **writer starvation** under continuous read load; fair
mode fixes it at a throughput cost. And it only pays off when reads massively dominate and the critical
section is non-trivial — otherwise a plain `ReentrantLock` is faster, and `StampedLock`'s optimistic
read is faster still.

→ `quiz/18` Q11; `quiz/03` Q7
</details>

### 44. What is a `java.util.concurrent.ForkJoinPool` in Java, and how is it used?

<details><summary>Answer</summary>

A pool built for **divide-and-conquer**: each worker owns a **deque**, pushes/pops its own subtasks LIFO
for cache locality, and **steals from the tail** of a victim's deque when idle. That's why it handles
uneven subtasks well.

```java
class Sum extends RecursiveTask<Long> {
    protected Long compute() {
        if (hi - lo < THRESHOLD) return sequential();
        var left = new Sum(lo, mid); left.fork();
        return new Sum(mid, hi).compute() + left.join();
    }
}
```

Measured on JDK 21.0.11 (14 cores): `commonPool()` parallelism **13** (`cores − 1`, because the
submitting thread helps), while `new ForkJoinPool()` and `newWorkStealingPool()` both report the **full
14** — the −1 is common-pool-only.

**`ManagedBlocker`** is the escape hatch for blocking inside an FJP: it tells the pool to compensate with
an extra thread. That's exactly what Scala's `blocking { }` marker does — relevant to the Scala side of
this role.

Backs `parallelStream()`, `CompletableFuture`'s default executor, and `Arrays.parallelSort`.

→ `quiz/18` Q23; `quiz/02` Q6
</details>

### 45. What is a `Semaphore`?

<details><summary>Answer</summary>

A permit counter: `acquire()` takes one (blocking if none), `release()` returns one. `new Semaphore(10)`
means "at most 10 concurrently".

It's the one synchroniser you'll actually use in production — bounding concurrent calls to a downstream
system, a crude bulkhead:

```java
if (!sem.tryAcquire(50, MILLISECONDS)) throw new OverloadedException();
try { callDownstream(); } finally { sem.release(); }
```

Unlike a lock, it isn't ownership-based: `acquire` and `release` need not be the same thread. That's the
flexibility *and* the bug source — **`release()` without a matching `acquire()` raises the permit
count**, silently widening your limit forever. Always `release` in a `finally`.

Can be constructed **fair** (FIFO) or unfair (barging, higher throughput; the default). A
`Semaphore(1)` is a non-reentrant mutex — which is occasionally what you want.

→ `quiz/18` Q9
</details>

### 46. What is the `ConcurrentHashMap.computeIfAbsent()` method in Java, and how is it used?

<details><summary>Answer</summary>

Atomic get-or-create: `map.computeIfAbsent(key, k -> expensive(k))`. The function is invoked **exactly
once** if the key is absent, and not at all if present.

It's the right answer to the check-then-act race — `containsKey`/`get`/`put` is two lookups and not
atomic. `P04` measured the difference: 8 threads, the loader ran 8 times, 7 results discarded.

**But the function runs while holding the bin lock**, so three documented rules follow:
1. Keep it **short** — other writers to that bin are blocked.
2. It **must not modify the same map**. Recursion can deadlock; the map throws
   `IllegalStateException: Recursive update` only when it **detectably** would never complete, so it is
   not a reliable guard.
3. Returning `null` **removes** the entry (or leaves it absent).

`merge(k, v, fn)` is the accumulation equivalent.

→ `quiz/18` Q14
</details>

### 47. What is a `ConcurrentLinkedDeque` in Java, and how is it used?

<details><summary>Answer</summary>

An **unbounded, lock-free** (CAS-based) double-ended queue — insert and remove at both ends, no blocking,
no capacity.

Distinguish the four in this corner:

| Class | Blocking? | Bounded? | Ends |
|---|---|---|---|
| `ConcurrentLinkedQueue` | no (lock-free) | no | tail in, head out |
| `ConcurrentLinkedDeque` | no (lock-free) | no | both |
| `LinkedBlockingQueue` | **yes** | optional | tail in, head out |
| `LinkedBlockingDeque` | **yes** | optional | both |

Choose lock-free when you never want a consumer to block (you'd poll, and do something else if empty) and
blocking when you want producer/consumer handoff with **backpressure**. `size()` on the lock-free ones is
**O(n)** and only an estimate — don't use it for control flow.

→ `quiz/18` Q18
</details>

### 48. What is the difference between `StringBuffer` and `StringBuilder` in Java, and when would you use one over the other?

<details><summary>Answer</summary>

Identical APIs; `StringBuffer` **synchronises every method**, `StringBuilder` doesn't.

**Use `StringBuilder`.** Always, in practice — a builder is almost always a local variable confined to
one thread, so the synchronisation is pure overhead, and a `StringBuffer` shared across threads is
usually a design mistake anyway (per-method atomicity doesn't make a *sequence* of appends atomic).
`StringBuffer` is a pre-1.5 legacy class.

The related question they're really testing: **`String` `+` in a loop is O(n²)**, because `String` is
immutable and each `+=` copies everything so far. The compiler *does* optimise `+` within a single
expression (via `StringConcatFactory`/`invokedynamic` since JDK 9) but **cannot** across loop iterations.

→ `quiz/16` Q10
</details>

### 49. What is a `Thread.UncaughtExceptionHandler` interface in Java, and how is it used?

<details><summary>Answer</summary>

The last-resort hook for an exception that propagates out of `run()`:

```java
Thread.setDefaultUncaughtExceptionHandler((t, e) -> log.error("died: {}", t.getName(), e));
```

Precedence: the thread's own handler → its `ThreadGroup`'s → the **default**. Set the default in `main`
for any production service; the fallback behaviour is a stack trace to `System.err`, which in a container
may go nowhere.

**The trap:** `executor.submit(task)` wraps the task in a `FutureTask` that **captures** the exception in
the `Future`, so the handler is **not** called and nothing is logged unless someone calls `get()`.
`execute()` does reach the handler. The standard fix is to override
`ThreadPoolExecutor.afterExecute(Runnable, Throwable)` — and note it must unwrap the `FutureTask` to see
the failure.

An uncaught exception kills only that thread, not the JVM.

→ `quiz/18` Q26
</details>

### 50. What is a `ThreadLocalRandom.current()` method in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q25 covered why it exists — this angle is the API contract.)*

`current()` returns **the calling thread's own** `ThreadLocalRandom` instance, initialising its seed on
first use. It's the only way to obtain one — the constructor is private and `setSeed` throws
`UnsupportedOperationException`.

```java
int venue = ThreadLocalRandom.current().nextInt(venues.size());
long jitter = ThreadLocalRandom.current().nextLong(50, 250);   // bounded overloads, JDK 8+
```

The contract you must not break: **never store or share the returned reference.** Call `current()` at
each use site. It's designed to be free — the call resolves to a field read on the `Thread` — so caching
it buys nothing and reintroduces the contention (and races) you were avoiding.

Extra API `Random` lacks: bounded `nextLong(origin, bound)` and `nextDouble(origin, bound)`, and the
`ints()`/`longs()`/`doubles()` stream factories.

→ `quiz/18` Q25
</details>

### 51. What is the `Arrays.parallelSort()` method in Java, and how is it used?

<details><summary>Answer</summary>

A parallel merge sort on the **common `ForkJoinPool`**, needing **O(n) extra space**.
`Arrays.parallelSort(arr)` — same signature family as `sort`.

The commonly quoted "8192 threshold" is only part of the truth. Read out of JDK 21.0.11's `src.zip`:

| Overload | Threshold |
|---|---|
| `T[]` / `T[]` + `Comparator` | **8192** (`Arrays.MIN_ARRAY_SORT_GRAN`) — used *only* in the object paths |
| `int[]`, `long[]`, `float[]`, `double[]` | **4096** (`DualPivotQuicksort.MIN_PARALLEL_SORT_SIZE`), and also requires `parallelism > 1` |
| `byte[]`, `char[]`, `short[]` | **never parallel** — no parallelism parameter exists on that path |

So a "parallel" sort of a `byte[]` is silently sequential at any size.

Worth adding: `Arrays.sort` itself uses **two** algorithms — dual-pivot quicksort for primitives
(in-place, unstable, fine because equal primitives are indistinguishable) and **TimSort** for objects
(stable, O(n) on nearly-sorted input, and the thing that throws when your comparator is inconsistent).

→ `quiz/17` Q17
</details>

### 52. What is a `CompletableFuture.thenCompose()` method in Java, and how is it used?

<details><summary>Answer</summary>

**`flatMap`.** Use it when your function itself returns a `CompletableFuture`, so the result doesn't
nest:

```java
findUser(id).thenCompose(this::loadAccount);        // CompletableFuture<Account>
findUser(id).thenApply(this::loadAccount);          // CompletableFuture<CompletableFuture<Account>>
```

That's the entire distinction from `thenApply`, and it's the same monadic pattern as `Stream.map`
vs `flatMap`, `Optional.map` vs `flatMap`, and Scala `Future.map` vs `flatMap`. Recognising it as **one
idea** rather than four API quirks is what an FP question is actually probing — directly relevant to the
Scala half of this role.

`thenComposeAsync` moves the *composition* to another thread; the inner future runs wherever it was
created.

→ `quiz/18` Q5; `quiz/12` Q7
</details>

### 53. What is a `CompletableFuture.thenAccept()` method in Java, and how is it used?

<details><summary>Answer</summary>

`thenAccept(Consumer<T>)` — consume the result and produce `CompletableFuture<Void>`. The terminal step
of a pipeline when you want a side effect rather than a value:
`f.thenAccept(t -> auditLog.record(t))`.

The trio, by what they take: `thenApply(Function)` → transforms; **`thenAccept(Consumer)`** → consumes;
`thenRun(Runnable)` → ignores the value entirely.

Same thread caveat as all non-`Async` stages: it runs on whoever completed the previous stage, or on the
calling thread if that stage is already done. Since `thenAccept` bodies are usually I/O or logging, this
is the one where hijacking a caller's thread most often actually hurts.

And the failure mode: a `Void`-returning tail that nobody observes means an **exception here is silently
swallowed**. Terminate with `whenComplete` or `exceptionally`.

→ `quiz/18` Q4, Q6
</details>

### 54. What is a `CompletableFuture.anyOf()` method in Java, and how is it used?

<details><summary>Answer</summary>

`anyOf(cf1, cf2, …)` → `CompletableFuture<Object>`, completing with the **first** stage to finish.

Two things make it awkward, and both are the answer:
1. It's **untyped** (`Object`), because the inputs may have different types — you cast, or use
   `thenApply` on each input first to normalise.
2. It completes with the **first outcome, including the first failure.** So it is *not* "first success
   wins" and is a poor fit for hedged requests unless you make each input swallow its own failure first
   (e.g. `.exceptionally(ex -> null)` then filter).

It also does **not cancel** the losers — they keep running and burning capacity.

For two typed futures prefer `thenCombine`; for real hedging on JDK 21, structured concurrency's
"first successful" joiner expresses it properly.

→ `quiz/18` Q7
</details>

### 55. What is a `CompletableFuture.allOf()` method in Java, and how is it used?

<details><summary>Answer</summary>

`allOf(cf1, cf2, …)` → **`CompletableFuture<Void>`**, completing when all inputs do. The signature is
the frequently-cursed part: it gives you no results, so you re-read the inputs:

```java
CompletableFuture.allOf(futures)
    .thenApply(v -> Arrays.stream(futures).map(CompletableFuture::join).toList());
```

`join()` is safe there because completion is already guaranteed.

Behaviour to state: it completes **exceptionally if any input fails**, but it does **not cancel** the
others, and it waits for all of them regardless. If you want "collect the successes, ignore failures",
attach `.exceptionally(...)` to each input *before* passing it in.

Common fan-out shape for this domain: load a trade's SSIs, positions and reference data concurrently,
then combine — with a per-call timeout via `orTimeout` so one slow dependency can't hold the request.

→ `quiz/18` Q7
</details>

### 56. What is a `java.util.concurrent.ConcurrentHashMap.KeySetView` in Java, and how is it used?

<details><summary>Answer</summary>

The `Set` view of a `ConcurrentHashMap`'s keys, and — via **`ConcurrentHashMap.newKeySet()`** — the
JDK's **concurrent `Set`**. There is no `ConcurrentHashSet` class; this is the replacement.

```java
Set<String> seen = ConcurrentHashMap.newKeySet();       // backed by CHM with Boolean.TRUE values
seen.add(tradeId);
```

The `mappedValue` form matters for `add`: `map.keySet(V mappedValue)` returns a view where `add` inserts
that common value — usable only when one value can serve every addition, and it **throws
`NullPointerException` if `mappedValue` is null**. The plain no-arg `keySet()` view has a null mapped
value, so its `add`/`addAll` throw `UnsupportedOperationException`.

It's a **view**: removals write through to the map. The alternative for read-mostly sets is
`CopyOnWriteArraySet`, but that's **O(n) `contains`** — fine for a handful of listeners, wrong for
anything larger.

→ `quiz/18` Q15
</details>

### 57. What is a `ReadWriteLock` in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q43 covered `ReentrantReadWriteLock`'s behaviour — this angle is the interface and the alternatives.)*

`ReadWriteLock` is the **interface**: two methods, `readLock()` and `writeLock()`, each returning a
`Lock`. It expresses the policy "many readers **or** one writer", nothing more — all the interesting
behaviour (fairness, reentrancy, starvation, downgrade) belongs to the implementation.

The JDK ships exactly **one** implementation: `ReentrantReadWriteLock`. `StampedLock` deliberately does
**not** implement this interface — it isn't reentrant and its modes are stamp-based — though it offers
`asReadLock()`/`asWriteLock()` adapter views.

Coding to the interface is worth it when you might swap in a fair vs unfair policy, and it makes the
intent visible at the field declaration. What it can't do is protect you from the upgrade deadlock —
that's an implementation property the interface says nothing about.

→ `quiz/18` Q11
</details>

### 58. What is the `Lock` interface in Java, and how is it used?

<details><summary>Answer</summary>

The explicit alternative to `synchronized`: `lock()`, `unlock()`, `tryLock()`,
`tryLock(timeout, unit)`, `lockInterruptibly()`, `newCondition()`.

```java
lock.lock();
try { … } finally { lock.unlock(); }        // the finally is mandatory
```

**What it buys you over `synchronized`:** `tryLock` with a timeout (the basis of deadlock avoidance),
interruptible acquisition, locking that isn't block-scoped (hand-over-hand), multiple `Condition`s per
lock, and optional fairness.

**What it costs:** the `try`/`finally` is on you — forget `unlock()` and the lock is held forever, where
`synchronized` releases even on exception.

Two more reasons it matters here: `tryLock` + randomised backoff is the standard alternative to global
lock ordering for deadlock avoidance (measured in `problems/java/P03`), and on **JDK 21 virtual threads**
`ReentrantLock` is the *preferred* choice because `synchronized` **pins** the carrier thread and
`ReentrantLock` doesn't.

→ `quiz/18` Q11; `quiz/01` Q11; `quiz/03` Q3
</details>

### 59. What is a `CopyOnWriteArrayList` in Java, and how is it used?

<details><summary>Answer</summary>

A thread-safe `List` where **every mutation copies the whole backing array** under a lock, and reads are
completely lock-free.

So: reads are fast and contention-free; writes are **O(n)** and allocate. Right for **small,
read-mostly** collections — listener and handler registries populated at startup and read constantly.
Wrong for 10,000 elements with regular writes.

The pleasant property: **iterators see an immutable snapshot** taken at creation. They never throw
`ConcurrentModificationException` (fail-**safe**), and correspondingly they don't see later writes and
`Iterator.remove()` is unsupported.

The subtle trap in that: `for (Listener l : listeners) l.fire();` can notify a listener that was removed
mid-iteration.

→ `quiz/18` Q18
</details>

### 60. What is the `CopyOnWriteArraySet` in Java, and how is it used?

<details><summary>Answer</summary>

A `Set` **backed by a `CopyOnWriteArrayList`** — same copy-on-write semantics, with uniqueness enforced
by scanning.

Which means the cost profile is worse than people expect: **`contains` is O(n)** and `add` is O(n) for
the scan *plus* O(n) for the copy. There's no hashing at all.

Use it only for tiny, read-mostly sets where snapshot iteration is the point — a handful of listeners.
For anything else, **`ConcurrentHashMap.newKeySet()`** is the better concurrent `Set`: O(1) `contains`,
per-bin write locking.

Shares the useful properties: no `ConcurrentModificationException`, snapshot iterators, no external
synchronisation needed for compound read operations.

→ `quiz/18` Q18, Q15
</details>
