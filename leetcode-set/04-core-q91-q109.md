# Q91–Q109 — `Future`, `CompletionService`, the rest of the `j.u.c.` inventory

---

### 91. What is the `java.util.concurrent.Executors.newSingleThreadExecutor()` method in Java, and how is it used?

<details><summary>Answer</summary>

One worker thread, an **unbounded `LinkedBlockingQueue`**, tasks executed **sequentially** in submission
order.

Its genuine value is that guarantee: it gives you **serial execution without locks**, so state touched only
by tasks on this executor needs no synchronisation. Useful for a single writer to a file, an ordered
event applier, or replacing a hand-rolled "one background thread" pattern.

Two specifics worth knowing:
- It's returned **wrapped** in a delegating class, so — unlike `newFixedThreadPool(1)` — it **cannot be
  cast to `ThreadPoolExecutor`** and reconfigured to more threads (measured on JDK 21.0.11:
  `instanceof ThreadPoolExecutor` → `false` vs `true`). That's deliberate: it protects the sequencing
  guarantee.
- If the single thread dies from an uncaught exception, a **new one replaces it** — so the executor keeps
  working, quietly, which is exactly why you want an `afterExecute` hook that logs.

Same unbounded-queue memory risk as `newFixedThreadPool`.

→ `quiz/18` Q22
</details>

### 92. What is the `java.util.concurrent.Future.get()` method in Java, and how is it used?

<details><summary>Answer</summary>

Blocks until the task finishes, then returns its result — or throws.

Three exceptions, and knowing which is which is the point:
- **`ExecutionException`** — the task threw. The real cause is in `getCause()`.
- **`InterruptedException`** — *you* were interrupted while waiting. It **clears the interrupt flag**, so
  either propagate it or restore the flag with `Thread.currentThread().interrupt()`.
- **`CancellationException`** — the task was cancelled.

**Always prefer `get(timeout, unit)`.** An unbounded `get()` is how a thread pool deadlocks: a task that
`get()`s on another task submitted to the same single-threaded pool waits forever. `TimeoutException`
means "not done yet" — it does **not** cancel anything, so you usually want `cancel(true)` after it.

Contrast `CompletableFuture.join()`: same blocking, but unchecked `CompletionException`, which is why
it's usable inside a lambda.

→ `quiz/18` Q1, Q8, Q28
</details>

### 93. What is the `java.util.concurrent.Future.isDone()` method in Java, and how is it used?

<details><summary>Answer</summary>

Returns `true` once the task has **finished in any way** — normal completion, exception, **or
cancellation**.

That breadth is the trap: **`isDone()` is not a success check.** To learn the outcome you still have to
call `get()` and handle the exceptions, or check `isCancelled()` first.

It's also useless as a spin condition — `while (!f.isDone()) {}` burns a core for nothing. Use
`get(timeout, unit)`, or `CompletableFuture`'s callbacks so you never poll at all.

Its legitimate uses are narrow: a non-blocking "have we finished?" for a status endpoint or progress
display, and filtering a collection of futures for the ones ready to read without blocking.

→ `quiz/18` Q8
</details>

### 94. What is the `java.util.concurrent.Future.isCancelled()` method in Java, and how is it used?

<details><summary>Answer</summary>

`true` if the task was cancelled **before completing normally**. Then `isDone()` is also `true`, and
`get()` throws `CancellationException`.

Use it to distinguish "cancelled" from "failed" when draining a batch, so you don't log a cancellation as
an error.

The important companion fact is what `cancel(mayInterruptIfRunning)` actually does. For a `FutureTask`
from `ExecutorService.submit`: if the task hasn't started, it never will; if it's running,
`mayInterruptIfRunning=true` **interrupts** the worker thread — and that only stops the task if the task
checks `Thread.interrupted()` or blocks in an interruptible call. Uninterruptible work (a tight compute
loop, most socket reads) runs to completion regardless.

And the asymmetry to have ready: **`CompletableFuture.cancel()` never interrupts anything** — it just
completes the future exceptionally while the work continues.

→ `quiz/18` Q8; `quiz/01` Q14
</details>

### 95. What is the `java.util.concurrent.CompletionService` interface in Java, and how is it used?

<details><summary>Answer</summary>

Decouples submitting tasks from consuming results **in completion order**.

```java
var cs = new ExecutorCompletionService<Quote>(pool);
venues.forEach(v -> cs.submit(() -> fetch(v)));
for (int i = 0; i < venues.size(); i++) process(cs.take().get());   // whoever finishes first
```

The problem it solves: iterating `List<Future>` and calling `get()` blocks in **submission** order, so one
slow first task makes you wait even though later results are ready. `ExecutorCompletionService` wraps an
executor plus an internal `BlockingQueue` and hands you whatever completed first.

Use it when you can act on partial results — first-response-wins quote fetching, streaming results to a
client as they arrive. `poll(timeout)` gives you a deadline so you can take what's ready and cancel the
rest.

`CompletableFuture.allOf`/`anyOf` covers much of this more expressively, so `CompletionService` mostly
appears in older code — but it remains the cleanest way to get **all** results **in completion order**.

→ `quiz/18` Q27
</details>

### 96. What is the `java.util.concurrent.LinkedBlockingQueue` in Java, and how is it used?

<details><summary>Answer</summary>

A linked blocking queue with **two locks** (head and tail), so producers and consumers contend less than
with `ArrayBlockingQueue`'s single lock — which is why it scales better under symmetric load.

**The fact that matters most: it is unbounded by default.** `new LinkedBlockingQueue<>()` has capacity
`Integer.MAX_VALUE`; you must pass a capacity to get backpressure:

```java
new LinkedBlockingQueue<Task>(1000)     // bounded -- put() now blocks, which is the point
```

That default is the single most consequential detail in `Executors`: it's what makes
`newFixedThreadPool` and `newSingleThreadExecutor` memory sinks, and it makes `maximumPoolSize` dead
configuration because the queue never rejects.

Method families by failure style: `put`/`take` block; `offer`/`poll` return boolean/null (optionally with
timeout); `add`/`remove` throw. Choose the family that matches your overload policy — and prefer
`offer(e, timeout, unit)` at a system boundary so you can shed load deliberately.

→ `quiz/18` Q16; `quiz/02` Q3
</details>

### 97. What is the `java.util.concurrent.ConcurrentHashMap.computeIfPresent()` method in Java, and how is it used?

<details><summary>Answer</summary>

Atomically remaps a key **only if it's already there**: `map.computeIfPresent(id, (k, v) -> v.withStatus(SETTLED))`.
If the key is absent, nothing happens and it returns `null`. **Returning `null` from the function removes
the entry** — which is the idiomatic atomic conditional-remove.

The four-method family, worth being able to distinguish:

| Method | Runs when | `null` return means |
|---|---|---|
| `computeIfAbsent(k, f)` | key **absent** | leave absent |
| `computeIfPresent(k, f)` | key **present** | **remove** |
| `compute(k, f)` | always (value may be `null`) | remove / stay absent |
| `merge(k, v, f)` | always; `f` only if present | remove |

Same contract as `computeIfAbsent`: the function runs **atomically while holding the bin lock**, so keep
it short, don't modify the same map inside it, and don't put I/O in it. The `IllegalStateException:
Recursive update` guard only fires when the recursion is **detectably** non-terminating, so don't rely on
it to catch your mistake.

→ `quiz/18` Q14
</details>

### 98. What is the `java.util.concurrent.Phaser` class in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q33 covered the API — this angle is when a `Phaser` is genuinely the right choice.)*

Pick it over the simpler synchronisers when **any** of these is true:

1. **The party count changes at runtime.** Tasks that spawn subtasks can `register()`; finishing ones
   `arriveAndDeregister()`. A `CyclicBarrier` fixes its count at construction, so this is impossible.
2. **You need multiple rounds *and* a termination signal.** `getPhase()` increments monotonically and
   `onAdvance(phase, parties)` returning `true` terminates the phaser — `CountDownLatch` can't repeat and
   `CyclicBarrier` can't stop.
3. **You need to arrive without waiting** — `arrive()` versus `arriveAndAwaitAdvance()`. Neither of the
   others separates those.
4. **Many parties.** **Tiering** (constructing child phasers with a parent) reduces contention, which
   matters past a few dozen participants.

It also degrades gracefully where `CyclicBarrier` breaks: interruption doesn't poison it for everyone
(no `BrokenBarrierException` equivalent), though `forceTermination()` exists when you do want to abort
everybody.

The cost is conceptual load — phase numbers, registration accounting, and `onAdvance` semantics are easy
to get subtly wrong. Default to a latch; escalate to `Phaser` when you hit one of the four above.

→ `quiz/18` Q10
</details>

### 99. What is the `java.util.concurrent.CyclicBarrier` class in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q41 covered the mechanics — this angle is the barrier action and the failure model.)*

The **barrier action** is the feature people forget: `new CyclicBarrier(n, action)` runs `action` on the
**last thread to arrive**, after all have arrived and before any are released. So it's a safe place to
merge per-round results or advance shared state without extra locking — nothing else is running in the
barrier at that moment.

```java
var barrier = new CyclicBarrier(workers, () -> grid.commitRound());   // runs once per round
```

The failure model is the other half. `await()` throws:
- **`InterruptedException`** — you were interrupted;
- **`BrokenBarrierException`** — someone *else* was interrupted, timed out, or the barrier action threw;
- **`TimeoutException`** from `await(timeout, unit)`, which **also breaks the barrier**.

Once broken it stays broken until `reset()` — and `reset()` itself breaks it for anyone currently waiting.
So a single interrupted worker takes down the whole round. `getNumberWaiting()` and `isBroken()` let you
inspect it; `getParties()` is fixed for life.

→ `quiz/18` Q10
</details>

### 100. What is the `java.util.concurrent.CountDownLatch` class in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q40 covered the basics — this angle is the two idioms and the one-shot consequence.)*

**Idiom 1 — starting gun (count 1).** Every worker waits on the same latch, then one `countDown()`
releases them simultaneously. That's how you maximise the chance of a race actually manifesting, which is
why every concurrency test in `problems/java/` uses it:

```java
var start = new CountDownLatch(1);
for (int i = 0; i < n; i++) pool.submit(() -> { start.await(); hammer(); });
start.countDown();                          // all n threads go at once
```

**Idiom 2 — finish line (count n).** Each worker `countDown()`s on completion; the coordinator `await()`s
for all. This is also the simplest "wait for service initialisation" primitive: components count down as
they become ready.

**The one-shot consequence:** there's no reset, so you cannot reuse it for a second round — construct a
new one. And a `countDown()` that never happens (an exception before it) hangs every waiter forever, so put
it in a `finally` and use `await(timeout, unit)`. `getCount()` is for diagnostics only.

→ `quiz/18` Q9
</details>

### 101. What is the `java.util.concurrent.BrokenBarrierException` class in Java, and how is it used?

<details><summary>Answer</summary>

Not something you "use" — something thrown *to* you. It signals that a `CyclicBarrier` (or `Phaser`
awaiting a broken barrier) can no longer fulfil its contract, so your wait will never be satisfied.

A barrier becomes broken when:
- a waiting thread is **interrupted**,
- a waiting thread **times out** in `await(timeout, unit)`,
- the **barrier action throws**,
- someone calls **`reset()`** while threads are waiting.

Every current and subsequent `await()` then throws it until a successful `reset()`.

How to handle it: treat it as **"the round is dead"**, not as a retryable error. Abandon the round, clean
up, and either `reset()` from a coordinator or fail the whole operation. Catching it and looping back into
`await()` is a spin — the barrier is still broken.

Which is the honest argument for `Phaser` or a per-round latch in production code: one flaky worker
shouldn't be able to poison a shared synchroniser for everyone.

→ `quiz/18` Q10
</details>

### 102. What is the `java.util.concurrent.TimeoutException` class in Java, and how is it used?

<details><summary>Answer</summary>

A **checked** exception meaning "the operation didn't complete within the time you allowed". Thrown by
`Future.get(timeout, unit)`, `CompletableFuture.get(timeout, unit)`,
`ExecutorService.invokeAny/awaitTermination` paths, and `CyclicBarrier.await(timeout, unit)`.

**The critical semantics: it does not cancel anything.** The task is still running. So the correct handler
is almost always two lines:

```java
try { return f.get(300, MILLISECONDS); }
catch (TimeoutException e) { f.cancel(true); return fallback(); }
```

Distinguish it from the neighbours:
- **`TimeoutException`** — checked; "not done yet, still running".
- **`InterruptedException`** — checked; "someone asked *you* to stop", and it **clears the interrupt
  flag**, so restore it.
- **`CompletableFuture.orTimeout(...)`** — completes the stage with `TimeoutException` **wrapped in
  `CompletionException`**, so unwrap with `getCause()` when matching.

Every remote call in a trading system should have one of these paths wired; an unbounded `get()` is a
production incident waiting for a slow dependency.

→ `quiz/18` Q28
</details>

### 103. What is the `java.util.concurrent.TimeUnit` enum in Java, and how is it used?

<details><summary>Answer</summary>

An enum of time granularities — `NANOSECONDS` … `DAYS` — that exists to make units **explicit at the call
site** rather than hidden in a `long`.

```java
pool.awaitTermination(30, SECONDS);
SECONDS.sleep(1);                          // clearer than Thread.sleep(1000)
long ms = MILLISECONDS.convert(5, MINUTES);
NANOSECONDS.toMillis(System.nanoTime() - t0);
```

Useful members beyond the constants: `sleep`, `timedWait`, `timedJoin`, `convert`, and the `toXxx`
converters. Conversions **truncate** rather than round, and can overflow — `NANOSECONDS.convert(300, DAYS)`
saturates rather than wrapping.

The reason it's on an interview list at all is API design: it removed a whole class of bug — a bare
`await(30)` where the reader can't tell whether that's seconds or milliseconds. Every timed method in
`java.util.concurrent` takes a `(long, TimeUnit)` pair for exactly that reason. Modern alternative for new
APIs: take a `java.time.Duration`.

And a measurement note: use **`System.nanoTime()`** for elapsed time (monotonic), never
`currentTimeMillis()`, which can jump backwards on NTP correction.

→ `quiz/18` Q28
</details>

### 104. What is the `java.util.concurrent.atomic.AtomicLong` class in Java, and how is it used?

<details><summary>Answer</summary>

A `long` with lock-free atomic operations built on **CAS** (compare-and-swap): `incrementAndGet`,
`addAndGet`, `getAndSet`, `compareAndSet`, `updateAndGet(fn)`, `accumulateAndGet`.

It solves what `volatile` can't: `count++` is read-modify-write, so a `volatile long` still loses
increments. `AtomicLong` makes the whole operation atomic — and also provides the `volatile` visibility
guarantee.

How CAS works: read the value, compute the new one, swap **only if** the current value is still what you
read; retry on failure. Which is where its weakness comes from — **under heavy contention threads spin
retrying**, and throughput collapses.

**So for contended counters use `LongAdder`.** It stripes across cells (one per contending thread,
padded against false sharing) and only sums on `sum()`. Measured in `problems/java/P02`:
`LongAdder` beat `AtomicLong` by roughly 4× at high contention, while being *slower* uncontended and
giving only an approximate `sum()` during concurrent updates.

Also know the **ABA problem** — CAS sees "unchanged" if a value goes A → B → A. `AtomicStampedReference`
adds a version to fix it.

→ `quiz/01` Q9; `quiz/04` Q13
</details>

### 105. What is the `java.util.concurrent.DelayQueue` class in Java, and how is it used?

<details><summary>Answer</summary>

An **unbounded** blocking queue of `Delayed` elements where an element can only be taken **once its delay
has expired**.

```java
class Retry implements Delayed {
    public long getDelay(TimeUnit u) { return u.convert(dueAt - now(), NANOSECONDS); }
    public int compareTo(Delayed o)  { … }        // order by due time
}
```

The two surprising behaviours, which are the real answer: **`take()` blocks even when the queue is
non-empty** if the head hasn't matured, and `poll()` returns `null` on a non-empty queue for the same
reason. So `size()` counts elements you cannot yet get.

Natural fits: **retry with backoff**, cache-expiry sweeping, and scheduled settlement instructions — far
better than a `ScheduledExecutorService` task per item when there are many items, because it's one thread
and one queue.

Being unbounded, it can't apply backpressure — bound it yourself if producers can outrun expiry.

→ `quiz/18` Q21
</details>

### 106. What is the `java.util.concurrent.BlockingDeque` interface in Java, and how is it used?

<details><summary>Answer</summary>

`BlockingQueue` + `Deque`: blocking insert and remove at **both ends**. Every operation exists as a
First/Last pair in three failure styles.

| | Throws | Returns special | Blocks | Times out |
|---|---|---|---|---|
| Insert first | `addFirst` | `offerFirst` | **`putFirst`** | `offerFirst(e,t,u)` |
| Remove first | `removeFirst` | `pollFirst` | **`takeFirst`** | `pollFirst(t,u)` |

…and the same for `Last`. The inherited `put`/`take` map to `putLast`/`takeFirst`, so it behaves as a FIFO
queue unless you say otherwise.

The JDK's only implementation is **`LinkedBlockingDeque`**. Use the interface as your field type when the
double-ended-ness is what you're relying on: work stealing (own end LIFO, thieves take the other end),
urgent-first insertion without a comparator, or a bounded LIFO stack with blocking.

If you don't need both ends, `LinkedBlockingQueue` has a **two-lock** design that scales better than
`LinkedBlockingDeque`'s single lock.

→ `quiz/18` Q18
</details>

### 107. What is the `java.util.concurrent.ThreadPoolExecutor` class in Java, and how is it used?

<details><summary>Answer</summary>

The real thread pool — everything `Executors` returns is one of these with preset arguments. Construct it
directly:

```java
new ThreadPoolExecutor(
    corePoolSize, maximumPoolSize, keepAliveTime, unit,
    workQueue,          // BOUNDED
    threadFactory,      // NAMED threads -- makes thread dumps readable
    handler);           // deliberate rejection policy
```

**The admission algorithm, which explains all the surprising behaviour:**
1. Below `corePoolSize` → **create a thread**, even if others are idle.
2. Otherwise → **try to queue**.
3. Queue rejected → create a thread up to `maximumPoolSize`.
4. Otherwise → **reject** via the handler.

So with an **unbounded queue, step 3 never runs** and `maximumPoolSize` is dead configuration. That's the
single most useful thing to be able to say about pools, and `problems/java/P05` measures it.

Rejection policies: `AbortPolicy` (default, throws), **`CallerRunsPolicy`** (runs on the submitting
thread — natural throttling, usually the right choice), `DiscardPolicy`, `DiscardOldestPolicy`.

Hooks and controls worth knowing: `beforeExecute`/`afterExecute` (the standard place to log swallowed
exceptions and clean `ThreadLocal`s), `allowCoreThreadTimeOut(true)`, `prestartAllCoreThreads()`,
`getActiveCount`/`getQueue().size()` for metrics, and `shutdown()` (drain) vs `shutdownNow()` (interrupt
and return the queue).

→ `quiz/02` Q1–Q4
</details>

### 108. What is the `java.util.concurrent.LinkedBlockingQueue.take()` method in Java, and how is it used? ↺

<details><summary>Answer</summary>

*(Q96 covered the queue — this angle is `take()` itself.)*

`take()` removes and returns the head, **blocking indefinitely while the queue is empty**, and throwing
`InterruptedException` if the waiting thread is interrupted.

That exception is the whole point of the method for a worker loop, and it's where most consumer bugs live:

```java
while (!Thread.currentThread().isInterrupted()) {
    Task t;
    try { t = queue.take(); }
    catch (InterruptedException e) { Thread.currentThread().interrupt(); break; }   // restore + exit
    process(t);
}
```

Catching it and continuing **clears the interrupt flag** and makes the thread unstoppable — the classic
un-shutdownable worker. Either restore the flag and exit, or propagate.

`take()` versus its siblings: `poll()` returns `null` immediately, `poll(timeout, unit)` waits then
returns `null`, `remove()` throws `NoSuchElementException`. Use `poll(timeout, unit)` when the worker also
needs to do periodic housekeeping, and `take()` when it genuinely has nothing else to do.

Internally it uses the head lock and a `notEmpty` condition, so consumers don't contend with producers.

→ `quiz/18` Q16; `quiz/01` Q14
</details>

### 109. What is the `java.util.concurrent.Executors.newSingleThreadScheduledExecutor()` method in Java, and how is it used?

<details><summary>Answer</summary>

A **single-threaded** `ScheduledExecutorService`: run a task after a delay, or repeatedly.

```java
var sched = Executors.newSingleThreadScheduledExecutor(namedFactory("recon-%d"));
sched.schedule(this::sweep, 5, SECONDS);                        // once
sched.scheduleAtFixedRate(this::heartbeat, 0, 1, SECONDS);       // every 1s from start times
sched.scheduleWithFixedDelay(this::poll, 0, 1, SECONDS);         // 1s gap between finish and next start
```

**`AtFixedRate` vs `WithFixedDelay` is the question behind the question.** Fixed *rate* schedules by start
time, so if a run overruns the period, subsequent runs fire immediately back-to-back trying to catch up.
Fixed *delay* measures from the end of the previous run, so it can never pile up. For anything whose
duration varies — polling, reconciliation, cache refresh — use **fixed delay**.

Two hazards specific to this executor:
1. **An uncaught exception silently cancels the repeating task.** The schedule stops, nothing is logged,
   and your heartbeat is just gone. Wrap the body in try/catch — always.
2. **One thread means one slow task delays everything else** scheduled on it. Its queue is an unbounded
   `DelayedWorkQueue`.

It also isn't a cron: no calendar semantics, no persistence, no cluster coordination, and it drifts across
DST. For business-time scheduling use Quartz or a Spring `@Scheduled` with a cron expression — or, on a
distributed system, an external scheduler, since every instance would otherwise fire its own copy.

→ `quiz/02` Q5
</details>
