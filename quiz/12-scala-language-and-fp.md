### 1. `val` vs `var` vs `lazy val` vs `def` — all four.

<details><summary>Answer</summary>

| | evaluated | re-evaluated? | thread-safe init |
|---|---|---|---|
| `val` | **eagerly**, at construction | no — evaluated once | yes (final field) |
| `var` | eagerly | no, but **reassignable** | no |
| `lazy val` | **on first access** | no — memoised | **yes**, double-checked |
| `def` | **on every call** | **yes, every time** | n/a |

```scala
val a = { println("a"); 1 }        // prints "a" now
lazy val b = { println("b"); 2 }   // prints nothing yet
def c = { println("c"); 3 }        // prints nothing yet
b; b                               // prints "b" ONCE
c; c                               // prints "c" TWICE
```

**`val` is the default and you should have to justify a `var`.** A `val` compiles to a
`final` field, so it gets JMM **freeze semantics** — safely publishable across threads with
no synchronisation (quiz 01 Q25). That's the concurrency argument for immutability.

**`lazy val`** — for expensive initialisation, or to break an initialisation-order cycle.
Two things to know:
- **It's thread-safe**: it compiles to a bitmap plus a `synchronized` double-checked
  initialisation on the enclosing instance. So you get correct lazy init for free — no
  holder idiom needed (contrast quiz 09/P07).
- **It can deadlock.** Two threads initialising interdependent `lazy val`s in opposite orders
  will hang, and the source gives you no hint that a lock is involved. Also, on **JDK 21
  virtual threads that `synchronized` pins the carrier** (quiz 03 Q2). A genuinely famous
  Scala footgun, and a good detail to volunteer.

**`def`** — recomputes each call. Use for genuinely parameterised or effectful things; a `def`
returning a constant is a subtle performance bug in a hot path.

**The trap to name:** `val` makes the **reference** immutable, not the object.
`val buf = mutable.ListBuffer[Int]()` is still a mutable, unsynchronised structure — measured
losing updates under concurrency in `S02FutureTraps.scala` Part 2.

Also worth mentioning: in a `case class`, constructor params are `val` by default; `var`
fields in a case class break `hashCode` stability and are a bad idea (same argument as
quiz 09 Q5 / P11 Case C).
</details>

### 2. `case class` vs a regular class.

<details><summary>Answer</summary>

`case class` gives you, generated by the compiler:
1. **All constructor params become `val`s** (public, immutable).
2. **Structural `equals` and `hashCode`** over all params — so two instances with equal
   contents are equal, and it works correctly as a `Map` key.
3. **A readable `toString`** — `Order(123,acme)` rather than `Order@4f2a1b`.
4. **`copy(...)`** with named/default params, for derived instances.
5. **A companion `apply`** — so `Order(1, "x")` with no `new`.
6. **`unapply`** — so it works in **pattern matching** and destructuring.
7. **`Serializable`**, and `productArity`/`productIterator`.

```scala
case class Order(id: Long, customer: String, qty: Int = 1)
val o  = Order(1, "acme")
val o2 = o.copy(qty = 5)
o == Order(1, "acme", 1)          // true -- structural
val Order(id, cust, _) = o        // destructuring
```

**Use a case class for:** immutable data — DTOs, domain events, value objects, messages,
config, and the branches of a `sealed trait` ADT. Which is most of a well-designed
codebase's types.

**Use a regular class for:** things with **identity rather than value** semantics (a
connection, a service, a repository — where two instances with the same fields are *not*
interchangeable); things with genuine mutable state; things needing inheritance from a
class hierarchy; or where you need to hide the representation, since case-class params are
public by definition.

**Two caveats worth raising:**
- **Case classes shouldn't be extended** — inheritance breaks the generated `equals`
  symmetry (the same problem as quiz 09 Q5). The compiler discourages it; make them `final`.
- **`copy` is a shallow copy.** `case class Order(items: List[Item])` shares the list — fine
  when it's immutable, a bug when it isn't.

**The Java bridge to draw:** this is exactly Java's **`record`** (JDK 16+), and records are
Java deliberately adopting `case class`. Scala's version adds `copy`, named/default
parameters, and `unapply` for pattern matching. So for the data-modelling half of a
migration, the concepts map almost 1:1 — which is a reassuring thing to be able to say.
</details>

### 3. Pattern matching vs `if`/`else`. Why is it better, and where does it bite?

<details><summary>Answer</summary>

Pattern matching **destructures and dispatches at once**, and — crucially — the compiler can
check it.

```scala
sealed trait TradeEvent
final case class Executed(id: String, qty: Int, price: BigDecimal) extends TradeEvent
final case class Cancelled(id: String, reason: String)             extends TradeEvent
final case class Settled(id: String, date: LocalDate)              extends TradeEvent

def describe(e: TradeEvent): String = e match {
  case Executed(id, qty, px) if qty > 10000 => s"block trade $id: $qty @ $px"
  case Executed(id, qty, _)                 => s"trade $id: $qty"
  case Cancelled(id, reason)                => s"cancelled $id ($reason)"
  case Settled(id, date)                    => s"settled $id on $date"
}
```

**What it gives you over `if`/`else` chains:**
- **Exhaustivity checking.** Because the trait is `sealed`, the compiler knows every subtype
  and **warns if you miss one**. Add a `Failed` event later and every `match` that needs
  updating produces a warning at compile time. With `if (e.isInstanceOf[...])` you get a
  silent runtime fall-through. **This is the single biggest argument, and the one to lead
  with** — especially for a domain like post-trade where the event set grows.
- **Destructuring** in the same expression as the test — no cast, no accessor calls.
- **It's an expression**, so it returns a value and composes.
- Matches on type, structure, literals, sequences (`case Seq(a, b, rest @ _*)`), tuples,
  regex, and anything with an `unapply`.
- **Guards** (`if qty > 10000`) for conditions beyond shape.

**Where it bites:**
- **`sealed` only works within one file** (Scala 2) / one file or package (Scala 3's
  restrictions differ). Cross-module ADTs don't get exhaustivity.
- **Non-sealed types get no exhaustivity check** — you need a `case _` and you'll never be
  told when a new case appears.
- **A missing case throws `MatchError` at runtime** — so treat the exhaustivity *warning* as
  an error (`-Xfatal-warnings`, and in Scala 3 `-Wnonexhaustive` / `-Werror`). Turning that
  warning on is a genuinely good practice to mention.
- **Erasure**: `case l: List[String]` can't check the type parameter — it matches any `List`,
  with an unchecked warning.
- **Lowercase identifiers bind, they don't compare.** `case expected =>` creates a *new
  variable* shadowing `expected` and matches everything. Use backticks (`` case `expected` =>``)
  or an uppercase name. A classic and baffling bug.

**Java comparison:** JDK 21 has pattern matching for `switch` plus `sealed` interfaces and
records — converging on the same thing. If you can say "Java 21's sealed interfaces +
records + switch patterns is the same ADT-plus-exhaustive-match idea", that lands well.
</details>

### 4. What's a companion object? What do `apply` and `unapply` do?

<details><summary>Answer</summary>

A **companion object** is an `object` with the same name as a class, in the same file. It has
**access to the class's private members** and vice versa. It's where Scala puts what Java
would call `static` members — factories, constants, implicits, and type class instances.

```scala
final case class Money private (amountMinor: Long, ccy: Currency) {
  def +(other: Money): Money = {
    require(ccy == other.ccy, "currency mismatch")
    Money(amountMinor + other.amountMinor, ccy)
  }
}

object Money {
  // apply: called as Money(...)  -- a smart constructor with validation
  def apply(amountMinor: Long, ccy: Currency): Money = {
    require(amountMinor >= 0, "negative amount")
    new Money(amountMinor, ccy)
  }
  def fromMajor(major: BigDecimal, ccy: Currency): Money = ...
  val zeroUsd: Money = Money(0, Currency.USD)
}
```

- **`apply`** — makes the object *callable*. `Money(100, USD)` is sugar for
  `Money.apply(100, USD)`. Used for **factories and smart constructors**: make the real
  constructor `private` and validate in `apply`, so an invalid instance cannot exist. That's
  the Scala equivalent of the Builder pattern's `build()` validation (quiz 09 Q1) — and it's
  also how `List(1,2,3)`, `Some(x)`, and `Map(k -> v)` work.
- **`unapply`** — the **extractor**, the inverse of `apply`. It's what makes pattern matching
  work: `case Money(amt, ccy) =>` calls `Money.unapply(m)`, which returns
  `Option[(Long, Currency)]`. Case classes generate it for you; you write it by hand for
  custom extractors.

```scala
object PositiveQty {                                    // a custom extractor
  def unapply(i: Int): Option[Int] = if (i > 0) Some(i) else None
}
qty match { case PositiveQty(q) => ...; case _ => reject }
```
`unapplySeq` extracts a variable number of elements (`case Seq(a, b, _*)`).

**Say the design point:** the `apply`/`unapply` pair means **construction and
deconstruction are symmetric and user-definable**, so pattern matching isn't tied to the
concrete representation — you can change the internals and keep the extractor. That's
something Java's record patterns can't do (they destructure the actual components).
</details>

### 5. Higher-order functions, closures, currying, partial application.

<details><summary>Answer</summary>

**Higher-order function** — takes and/or returns a function. Functions are values.
```scala
def retry[A](attempts: Int)(op: () => A): A = ...      // takes a function
def multiplier(n: Int): Int => Int = x => x * n        // returns a function
xs.map(f).filter(p).foldLeft(0)(_ + _)                 // all HOFs
```

**Closure** — a function value that **captures** variables from its defining scope.
```scala
val threshold = 1000
val isBlock: Trade => Boolean = t => t.qty > threshold   // captures `threshold`
```
The capture is by **reference** to the variable, so capturing a `var` means the closure sees
later mutations — a real source of surprise, and in a concurrent context a data race
(measured in `S02FutureTraps.scala` Part 2). **Capture `val`s.** Each capturing closure is
also an allocation (quiz 06 D1).

**Currying** — a function of multiple arguments expressed as a chain of single-argument
functions. Scala spells it with **multiple parameter lists**:
```scala
def transfer(from: Account)(to: Account)(amount: Money): Result = ...
val fromMine = transfer(myAccount) _        // partially applied
```
Why it's actually useful in Scala, beyond theory:
1. **Type inference flows left to right across parameter lists**, so
   `def fold[B](z: B)(op: (B, A) => B)` can infer `B` from `z` and then check `op` against
   it. With one list it often can't. **This is the real reason the standard library curries.**
2. It enables the **implicit parameter list** (`(implicit ec: ExecutionContext)`).
3. It enables **by-name blocks that look like syntax**:
   `def using[R](r: Resource)(body: R => A): A` called as `using(conn) { c => ... }`.
4. Partial application for reuse and DI-by-closure.

**Partial application vs partial function** — different things, and worth distinguishing:
- **Partially applied**: supply some arguments, get a function back. `add(1) _`
- **`PartialFunction[A, B]`**: defined only for *some* inputs, with `isDefinedAt`. That's
  what a `case` block is, and it's why `collect` can filter and map at once:
  `xs.collect { case Executed(id, q, _) if q > 0 => id }`. Also what Akka's `receive` is.

**Java comparison:** lambdas plus `Function`/`BiFunction` cover HOFs, but Java has no
currying sugar, no by-name parameters, and no partial functions — so you get the concept and
not the ergonomics.
</details>

### 6. What is a monad? Give the laws, and explain how `Option`, `Either`, and `Future` behave as monads.

<details><summary>Answer</summary>

**Don't lead with category theory.** Lead with what it *is for*.

> A monad is a type with a `flatMap` and a way to lift a plain value in (`pure`/`apply`),
> obeying three laws. Practically: **it's a container or context you can sequence
> computations inside, where the context's plumbing is handled for you.**

```scala
trait Monad[F[_]] {
  def pure[A](a: A): F[A]
  def flatMap[A, B](fa: F[A])(f: A => F[B]): F[B]
  // map is derivable: flatMap(fa)(a => pure(f(a)))
}
```

**The three laws** (be able to state them; they're what make refactoring safe):
1. **Left identity:** `pure(a).flatMap(f) == f(a)`
2. **Right identity:** `fa.flatMap(pure) == fa`
3. **Associativity:** `fa.flatMap(f).flatMap(g) == fa.flatMap(a => f(a).flatMap(g))`

The payoff of the laws is that **`for`-comprehensions mean what you expect** and you can
re-nest and factor out steps without changing behaviour.

**What "the plumbing" is, per type — this is the part that actually answers the question:**

| Monad | Context it handles | `flatMap` short-circuits when |
|---|---|---|
| `Option[A]` | **absence** | it's `None` — no null checks, no nesting |
| `Either[E, A]` | **failure with a reason** | it's a `Left` — the error is carried, right-biased since 2.12 |
| `Try[A]` | **thrown exceptions** | it's a `Failure` — catches `NonFatal` |
| `Future[A]` | **asynchrony** (and failure) | it fails — plus it sequences on an `ExecutionContext` |
| `List[A]` | **multiplicity** | never — it's the cartesian product |
| `IO`/`ZIO` | **effects**, lazily described | it fails or is cancelled |

```scala
// Every one of these is the same shape, and that's the point:
for { a <- optA; b <- optB(a) } yield a + b     // None anywhere -> None
for { a <- eiA;  b <- eiB(a)  } yield a + b     // Left anywhere -> that Left
for { a <- futA; b <- futB(a) } yield a + b     // failure anywhere -> failed Future
```
**The uniformity *is* the value:** one syntax for absence, error, async, and multiplicity, so
you write the happy path and the context propagates.

**Two things that make the answer sound experienced:**
- **`Future` is arguably not a lawful monad**, because it's **eager** and side-effecting:
  `pure(a).flatMap(f)` isn't substitutable for `f(a)` when effects are involved, and `Future`
  memoises. It behaves monadically for composition purposes, which is why the syntax works,
  but referential transparency is broken — see quiz 06 A3 and the measurement in
  `S02FutureTraps.scala` Part 4. `IO`/`ZIO` are lawful.
- **`for` over different monads doesn't mix.** You can't `flatMap` an `Option` into a
  `Future` in one comprehension. That's what **monad transformers** (`OptionT`, `EitherT`) or
  just converting (`Future.fromTry`, `opt.toRight(err)`) are for. Naming that problem shows
  you've written real code in this style.

**Related vocabulary they may probe:** a **functor** has `map`; an **applicative** adds
`pure` and independent combination (`(fa, fb).mapN` — which can **accumulate** errors,
unlike monadic `flatMap` which short-circuits — that's why `Validated` is an applicative and
not a monad); a **monoid** has an associative `combine` and an identity.
</details>

### 7. `Future` vs `Promise`?

<details><summary>Answer</summary>

- **`Future[A]`** is the **read side** — a read-only handle to a value that may not exist
  yet. You can `map`, `flatMap`, `onComplete`, `recover`. You **cannot complete it**.
- **`Promise[A]`** is the **write side** — you complete it exactly once, with
  `success`, `failure`, `complete(Try)`, or `tryComplete`. It exposes `.future` for readers.

One `Promise` has one `Future`. Completing twice throws `IllegalStateException` (hence
`tryComplete`, which returns a `Boolean`).

```scala
val p = Promise[Quote]()
amps.subscribe("quotes") { msg => p.trySuccess(parse(msg)) }   // producer completes it
val f: Future[Quote] = p.future                                 // consumer only reads
```

**When you actually need a `Promise`:** bridging a **callback-based or push-based API** into
`Future`. That's the canonical use, and it's exactly relevant here — wrapping a Kafka
consumer callback, a JMS listener, an AMPS subscription, a Netty channel future, or a legacy
Java library's listener interface. `Future { ... }` can't do that, because it assumes you
have a *block of code* to run rather than an event that will arrive.

Also useful for: an in-flight-request registry (`Map[CorrelationId, Promise[Response]]` for
request/reply over a message bus — a very common post-trade pattern), and the
single-flight caching trick (verified in `P09Exercises` EX4, where a `CompletableFuture` is
used as the map value so racing callers share one load).

**The Java analogy:** `CompletableFuture` conflates both roles in one class — it's both the
handle *and* completable (`complete()`, `completeExceptionally()`). Scala splits them, which
is better encapsulation: you hand out the `Future` and keep the `Promise`, so a consumer
*cannot* complete your future. Worth saying — it's a genuine design improvement.

**In effect-system terms:** `Deferred[IO, A]` (Cats Effect) or `Promise` (ZIO) is the same
concept, but **semantically blocking** — `get` parks the fiber, not a thread (quiz 06 C3).
</details>

### 8. `Option` vs `null`; `Either` vs `Try` vs `Validated`. When do you use each?

<details><summary>Answer</summary>

**`Option` vs `null`:** `Option` makes absence **visible in the type** and forces the caller
to handle it — the compiler is the enforcement, not discipline. It composes (`map`, `flatMap`,
`getOrElse`, `orElse`, `fold`, `toRight`), so you don't write null-check pyramids.

Costs to be honest about: `Some(x)` is an allocation (16 bytes, and it boxes primitives —
quiz 06 D1), and **`.get` on a `None` throws**, so `Option` misused is just `null` with extra
steps. Never `.get`; use `getOrElse`, `fold`, or pattern matching. Also `Option` is
`null`-blind: `Option(javaMethodThatMayReturnNull)` is the correct way to wrap Java APIs,
because `Option(null) == None` whereas `Some(null)` is a legal, horrible value.

**Choosing an error type:**

| Type | Carries | Use when |
|---|---|---|
| `Option[A]` | nothing — just absence | "not found" and the caller doesn't need a reason |
| `Either[E, A]` | a **typed** error `E` | **domain errors you enumerate.** The default for business logic |
| `Try[A]` | a `Throwable` | wrapping code that **throws** — Java interop, parsing, I/O |
| `Validated[NEL[E], A]` | **accumulated** errors | **validation**, where you want *all* the failures, not the first |
| `IO`/`ZIO[R,E,A]` | effects + errors | effectful code; ZIO puts `E` in the type |

The distinction most worth articulating: **`Either`/`Try` short-circuit (monadic), `Validated`
accumulates (applicative).**
```scala
// Short-circuits: reports only the FIRST problem
for { a <- validateQty(t); b <- validateCcy(t); c <- validateDate(t) } yield Trade(a,b,c)

// Accumulates: reports ALL problems -- what an API's 400 response should do
(validateQty(t), validateCcy(t), validateDate(t)).mapN(Trade.apply)
```
For a trade-validation endpoint you almost always want the second. That's a concrete,
domain-relevant example and a strong thing to volunteer.

**Idiomatic pattern:** a `sealed trait DomainError` ADT + `Either[DomainError, A]` internally,
mapped to HTTP status once at the edge (quiz 10 Q7). The compiler then tells you when a new
error case isn't handled — which is what checked exceptions were *supposed* to achieve
without the syntactic tax (quiz 09 Q11).
</details>

### 9. Implicits — parameters, conversions, and how do you use them safely?

<details><summary>Answer</summary>

Scala 2 overloads the word `implicit` for three genuinely different things. Say that first,
because the safety answer differs per use.

**1. Implicit parameters — safe and idiomatic.** Passing context without threading it
manually.
```scala
def save(t: Trade)(implicit ec: ExecutionContext): Future[Unit]
def process(t: Trade)(implicit correlationId: CorrelationId, clock: Clock): Result
```
This is the mechanism behind `ExecutionContext`, type class instances, and
`Ordering`/`CanBuildFrom`. **Fine, and preferable to a `ThreadLocal`** for context — see
quiz 07 Q3, where `ThreadLocal`-based context is the thing that breaks in an async port.

**2. Implicit classes / extension methods — safe.** Adding methods to types you don't own.
```scala
implicit class RichTrade(t: Trade) { def notional: Money = t.qty * t.price }
```
The "pimp my library" pattern. In **Scala 3 this is `extension`**, which is clearer.

**3. Implicit *conversions* — the dangerous one.**
```scala
implicit def stringToTradeId(s: String): TradeId = TradeId(s)   // DON'T
```
Now any `String` silently becomes a `TradeId` anywhere the compiler wants one. It makes code
**unreadable** (invisible behaviour at the call site), **hard to debug**, and it can hide type
errors that should have failed. Scala 3 requires an explicit `import
scala.language.implicitConversions` and steers you to `Conversion` — deliberately harder.

**The safety rules to state:**
- **Use implicit parameters and extension methods freely; avoid implicit conversions almost
  always.** The exception is a narrow, well-known interop boundary (e.g. Java `Duration` ↔
  Scala `Duration`), scoped tightly.
- **Never make an implicit conversion between two types you own** — just call a method.
- **Put type class instances in the companion object** of the type, so they're found by
  implicit scope without an import. Predictable resolution beats clever resolution.
- **Import implicits narrowly** — `import MyImplicits.tradeOrdering`, not `._`. A wildcard
  implicit import is how you get ambiguity errors nobody can diagnose.
- **Prefer explicit** when the value is a *decision* rather than *context*. An implicit
  `ExecutionContext` is context; an implicit "should we retry" flag is a landmine.
- Watch **ambiguity** and **divergence** — two eligible implicits is a compile error whose
  message is often terrible; that's the tax.

**Scala 3 split them deliberately**, which is a good detail: `using`/`given` for parameters
and instances, `extension` for methods, `Conversion` for conversions. The confusion was
recognised as a design mistake and fixed.
</details>

### 10. What is a type class, and why would you use one?

<details><summary>Answer</summary>

**Ad-hoc polymorphism**: define behaviour for a type **without modifying the type**, and
without inheritance.

```scala
// 1. The type class -- a trait parameterised on the type
trait EventSerializer[A] {
  def serialize(a: A): Array[Byte]
  def deserialize(bytes: Array[Byte]): Either[DecodeError, A]
}

// 2. Instances, in the companion object so they're found automatically
object EventSerializer {
  implicit val executedSerializer: EventSerializer[Executed] = new EventSerializer[Executed] { ... }
  implicit val settledSerializer:  EventSerializer[Settled]  = new EventSerializer[Settled]  { ... }
}

// 3. Use it via an implicit parameter (a "context bound")
def publish[A: EventSerializer](topic: String, event: A): Future[Unit] = {
  val bytes = implicitly[EventSerializer[A]].serialize(event)
  ...
}
```
`[A: EventSerializer]` is a **context bound**, sugar for
`(implicit ev: EventSerializer[A])`.

**Why, over an interface/inheritance:**
- **Retroactive.** You can add `EventSerializer[java.time.Instant]` for a type you don't own.
  Inheritance requires modifying the class.
- **Decoupled.** Your domain type doesn't extend a serialisation interface, so the domain
  doesn't depend on the transport. That matters a lot in an event-sourced system — see
  quiz 13 Q4 on schema evolution.
- **Multiple instances per type.** Two different `Ordering[Trade]`s (by date, by notional)
  chosen at the call site. An interface gives you exactly one `compareTo`.
- **Coherent by scoping**, and resolved at **compile time** — no reflection, and a missing
  instance is a compile error, not a runtime one.
- Works for types you can't subclass — primitives, `String`, final Java classes.

**Where you already use them:** `Ordering`, `Numeric`, Circe's `Encoder`/`Decoder`, doobie's
`Get`/`Put`, Cats's `Monoid`/`Functor`/`Monad`, `ClassTag`.

**Costs, to be balanced:** more machinery than an interface; **cryptic compile errors** when
an instance is missing ("could not find implicit value for..."); implicit resolution can be
slow at compile time; and it's an unfamiliar idiom for a team coming from Java, which is a
real adoption cost worth acknowledging.

**Java comparison:** Java has no type classes. The closest thing is passing a `Comparator`
explicitly — which is exactly a type class instance, passed by hand instead of by the
compiler. That framing usually makes it click for a Java audience.
</details>

### 11. Tail recursion, `@tailrec`, and trampolining.

<details><summary>Answer</summary>

**The JVM has no tail-call optimisation.** Every call pushes a frame, so deep recursion gives
`StackOverflowError` — typically at 10 000–100 000 frames depending on frame size.

**`scalac` does self-tail-call elimination**: a method whose recursive call is in **tail
position** and which calls **itself** is rewritten into a `while` loop. Zero frames, zero
allocation, identical speed to the hand-written loop.

Requirements: the call must be the *last* thing evaluated, and the method must not be
overridable — so `private`, `final`, or inside an `object`.

```scala
import scala.annotation.tailrec

@tailrec
def replayEvents(events: List[TradeEvent], state: Position): Position = events match {
  case Nil     => state
  case e :: es => replayEvents(es, applyEvent(state, e))   // tail position: OK
}

// NOT tail-recursive -- the addition happens AFTER the call returns:
def sum(xs: List[Int]): Int = xs match {
  case Nil     => 0
  case x :: xs => x + sum(xs)        // the `+` is the last operation, not the call
}
```

**Always annotate `@tailrec`** — it makes it a **compile error** if the optimisation can't be
applied. Without it you get a silently stack-consuming method that works on your test data
and blows up on the one production input with 200 000 events. For an event-sourced system
replaying long streams, that's a real risk (quiz 13 Q6).

**What it can't do:** **mutual recursion** (`isEven`/`isOdd`) and non-self tail calls. For
those you need **trampolining** — instead of calling directly, *return a description* of the
next step, and have a driver loop execute the steps. The stack becomes heap:

```scala
import scala.util.control.TailCalls._
def isEven(n: Int): TailRec[Boolean] =
  if (n == 0) done(true) else tailcall(isOdd(n - 1))
def isOdd(n: Int): TailRec[Boolean] =
  if (n == 0) done(false) else tailcall(isEven(n - 1))
isEven(1_000_000).result      // no stack overflow
```
Also available as `cats.free.Trampoline` / `Eval.defer`.

**The point worth volunteering:** **this is exactly what `IO` and `ZIO` do for free.** Their
`flatMap` chains are interpreted by a **heap-allocated loop**, not the JVM stack, so
arbitrarily deep recursion inside `IO` is stack-safe with no `@tailrec` and no trampolining
by hand. That's an underrated benefit of effect systems and a natural bridge from this
question to quiz 06 C1.

**Alternatives to recursion:** `foldLeft` (which is itself a tail-recursive loop),
`Iterator`, or an explicit accumulator loop. And note `foldRight` on a `List` is **not**
stack-safe for large inputs in the general case.
</details>

### 12. `map` vs `flatMap` vs `filter` — and how does a `for`-comprehension desugar?

<details><summary>Answer</summary>

- **`map(f: A => B): F[B]`** — transform inside the context. Shape preserved.
- **`flatMap(f: A => F[B]): F[B]`** — transform **and flatten**. For when `f` itself returns
  the context, so `map` would give you `F[F[B]]`.
- **`filter`/`withFilter(p: A => Boolean)`** — keep matching elements. `withFilter` is lazy,
  and it's what `for`-guards actually call.

**Desugaring — be able to do this on a whiteboard, it comes up:**
```scala
for {
  trade    <- findTrade(id)             // flatMap
  account  <- findAccount(trade.acct)   // flatMap
  if account.isActive                   // withFilter
  enriched =  enrich(trade, account)    // a plain assignment
} yield enriched                        // map

// becomes:
findTrade(id).flatMap { trade =>
  findAccount(trade.acct)
    .withFilter(account => account.isActive)
    .map { account =>
      val enriched = enrich(trade, account)
      enriched
    }
}
```
**The rule: every `<-` except the last is a `flatMap`; the last one plus `yield` is a `map`;
guards are `withFilter`.** So a `for`-comprehension is pure syntax — anything with `map`,
`flatMap`, and `withFilter` works in one, including your own types.

**Two consequences worth naming:**
1. **`for` over `Future` is sequential**, because each subsequent `Future` is *constructed*
   inside the previous `flatMap` — measured at 920 ms vs 311 ms in `S02FutureTraps.scala`
   Part 1. This is the number-one Scala `Future` bug (quiz 06 A4).
2. **All monads in one comprehension must be the same type.** You can't mix `Option` and
   `Future`. Hence monad transformers, or converting first.

**`collect`** deserves a mention: it takes a `PartialFunction`, so it filters and maps in one
pass — `events.collect { case e: Executed => e.qty }` is cleaner than `filter` + `map` and
allocates one fewer collection.
</details>

### 13. Explain variance: `+A`, `-A`, and invariance.

<details><summary>Answer</summary>

Variance describes how subtyping of a type parameter relates to subtyping of the container.
Given `Dog <: Animal`:

- **Covariant `[+A]`** — `Box[Dog] <: Box[Animal]`. For **producers/outputs**. `List[+A]`,
  `Option[+A]`, `Future[+A]`. Safe because you only ever *read* `A` out, and a `Dog` is a
  valid `Animal`.
- **Contravariant `[-A]`** — `Box[Animal] <: Box[Dog]`. For **consumers/inputs**. A function
  that handles any `Animal` can be used where one handling `Dog`s is required.
- **Invariant `[A]`** — no relationship. Required when `A` appears in **both** positions, i.e.
  anything **mutable**. `Array[A]`, `mutable.ListBuffer[A]`.

**`Function1[-T, +R]`** is the canonical illustration: contravariant in its argument,
covariant in its result. `Animal => String` is a subtype of `Dog => String`.

**Why invariance is necessary for mutable containers** — the classic argument:
```scala
// IF Array were covariant (as Java's arrays wrongly are):
val dogs: Array[Dog] = Array(new Dog)
val animals: Array[Animal] = dogs        // allowed if covariant
animals(0) = new Cat                     // type-checks! but the array holds Dogs
val d: Dog = dogs(0)                     // ClassCastException at runtime
```
Java **does** allow this, and it's why you get `ArrayStoreException` at runtime — a
well-known unsoundness in Java's type system. Scala makes `Array` invariant and catches it at
compile time. **That's a great concrete answer**, because it shows variance isn't academic.

**The rule of thumb:** *"covariant out, contravariant in, invariant if both"* — the same
intuition as Java's **PECS** (Producer Extends, Consumer Super) for wildcards. If you can
name that equivalence, it lands well with a Java-heavy panel.

**Java comparison:** Java has **use-site** variance (`List<? extends Animal>` at every usage);
Scala has **declaration-site** variance (`List[+A]`, declared once). Scala's is less verbose
and harder to get wrong at the call site, at the cost of the library author having to think
about it — which is why you occasionally see a `+A` with a `[B >: A]` method signature (as on
`List.::`) to keep it sound.
</details>

### 14. Traits vs abstract classes. What's linearisation?

<details><summary>Answer</summary>

**`trait`** — can be **mixed in multiply**, can have abstract and concrete members, can have
fields (with limits) and type members. Cannot take constructor parameters in Scala 2 (Scala 3
allows them). The default choice.

**`abstract class`** — single inheritance only, but can take **constructor parameters** and
interoperates better with Java. Use it when you need a constructor, or when the type is a
genuine single-parent hierarchy.

**Linearisation** — how Scala resolves the diamond problem. Mixins are linearised
**right to left**, and `super` follows that order rather than a fixed parent.

```scala
trait Logging       { def process(t: Trade): Unit = println("base") }
trait Timed extends Logging { override def process(t: Trade): Unit = { /* time */ super.process(t) } }
trait Audited extends Logging { override def process(t: Trade): Unit = { /* audit */ super.process(t) } }

class Handler extends Logging with Timed with Audited
// linearisation: Handler -> Audited -> Timed -> Logging -> AnyRef -> Any
// so process() runs Audited's body, whose super.process is TIMED's, not Logging's
```
**The rule: last mixin wins, and `super` means "the next trait in the linearisation".** That
enables **stackable modifications** — decorators composed by mixin, which is a legitimate and
elegant use (the "cake pattern" ancestor).

The caveat to state: linearisation order is **not obvious from reading the class**, so deep
mixin stacks become genuinely hard to reason about. Which is why the modern advice is
**composition over mixin inheritance** — pass collaborators as constructor parameters, use
higher-order functions for cross-cutting behaviour (quiz 10 Q12), and keep traits shallow.

**`sealed trait`** is the important variant: restricts extension to the same file, which is
what enables **exhaustive pattern matching** (Q3) and makes it the standard way to define an
**ADT**. That's the use you'll actually reach for daily.

**Java comparison:** Java 8+ interfaces with `default` methods are close, but Java resolves
diamonds by *forbidding* the ambiguity (you must override), where Scala *orders* it. Scala
traits also allow state. Java's `sealed interface` + `record` (JDK 17+) is converging on
`sealed trait` + `case class`.
</details>

### 15. How do you handle concurrency idiomatically in Scala?

<details><summary>Answer</summary>

> **Fully covered in `quiz/06`** — this is a summary with pointers, because it's the
> intersection of this file and the JD's concurrency expectations.

**The hierarchy, best to worst:**
1. **Don't share mutable state.** Immutable values, `val`s, `case class`es, and pure
   transformations. Because immutability is the *default*, the whole class of shared-mutable
   bug becomes opt-in (quiz 06 D5, quiz 07 Q11).
2. **Confine mutation.** A `var` or `mutable.ArrayBuffer` inside a method body is
   **idiomatic** when it doesn't escape — the rule is "no observable mutation", not "no `var`".
3. **Make sharing explicit** when you need it: `Ref[IO, A]` / ZIO `Ref` / `AtomicReference`
   with a pure update function (quiz 06 C2).
4. **Single-writer by construction** — an actor's state, accessed only from `receive`
   (quiz 06 B1/B2).
5. **The database** for anything that must be shared across instances or survive restart.
6. **A lock** — the Java answer, and the thing you're migrating away from.

**And the two things that will actually bite you**, both measured:
- **Never block the compute `ExecutionContext`.** One blocking JDBC call on a cores-sized
  pool starves the whole application; on a fixed pool it can **deadlock** (reproduced in
  `S01BlockingGlobalEC.scala` Part 4). Two pools: compute sized to cores, and a **bounded**
  blocking pool sized to the downstream. Ban `ExecutionContext.Implicits.global` in
  production code with a lint rule.
- **Bound every fan-out.** `Future.traverse` over 5 000 items starts 5 000 concurrent
  operations — measured at 500-of-500 in flight in `S02FutureTraps.scala` Part 3. Use
  `parTraverseN(n)`, `ZIO.foreachPar(...).withParallelism(n)`, or `mapAsync(n)`.

**The honest summary of `Future`'s limits:** eager, so **no retry and no cancellation**, and
sequential-vs-parallel is a positional accident. If the team is pushing FP maturity, that's
the argument for Cats Effect or ZIO (quiz 07 Q8).
</details>

### 16. What problem do effect systems solve, and what is "tagless final"?

<details><summary>Answer</summary>

**What `IO`/`ZIO` solve** — everything that follows from `Future` being **eager**:
- **Referential transparency.** `IO` is a *description* of an effect, so `val x = io; x *> x`
  runs it twice, exactly as substituting the definition would. You can refactor by equational
  reasoning. `Future` can't (quiz 06 A3).
- **Retries and timeouts as combinators** — `io.retry(policy)`, `io.timeout(1.second)`. You
  cannot retry a `Future` because it's already run (measured: `S02FutureTraps.scala` Part 4).
- **Real cancellation with resource safety.** `Resource`/`Scope` guarantee release on success,
  failure, **and cancellation**. Java has no correct answer for this (measured: `P05` Part 6,
  where a 300 ms timeout returned a fallback while the work ran another 1.2 s).
- **Structured concurrency** — children don't outlive the parent scope; a failure cancels
  siblings.
- **Bounded parallelism** as a parameter (`parTraverseN`).
- **Stack safety** — flatMap chains are heap-interpreted (Q11).
- **Deterministic testing of time** — ZIO's `TestClock` / Cats Effect's `TestControl` let you
  `adjust(1.hour)` instantly, so testing an exponential-backoff schedule is a fast unit test
  (quiz 07 Q9). One of the strongest practical arguments.
- **ZIO additionally**: typed errors (`E`) and compile-time DI (`R`/`ZLayer`) (quiz 06 C5).

**Tagless final** — writing code against an **abstract effect type constrained by type
classes**, rather than committing to a concrete one:

```scala
// Not `IO`, but "some F with these capabilities":
trait TradeRepository[F[_]] {
  def find(id: TradeId): F[Option[Trade]]
  def append(e: TradeEvent): F[Unit]
}

class TradeService[F[_]: MonadThrow: Clock](repo: TradeRepository[F], bus: EventBus[F]) {
  def settle(id: TradeId): F[SettlementResult] =
    for {
      trade <- repo.find(id)
      ...
    } yield result
}
```
`F[_]` is the effect; `: MonadThrow` (a context bound, Q10) says "F must support sequencing
and raising errors". The *interpreter* is chosen at the edge.

**Why:**
- **Testability** — instantiate `F = Either[Throwable, *]`, `Id`, or a `WriterT` that records
  calls, so business logic tests run synchronously with no runtime.
- **Least power / capability tracking** — the constraints *document* what a method can do. A
  method with only `Monad[F]` provably can't perform I/O or fail.
- **Portability** — the same code runs on `IO`, `ZIO`, or `Future`.

**The honest costs, and say them:** it's **a significant abstraction tax**. Everything gains
an `F[_]`, type inference gets worse, error messages get much worse, and it's a steep step
for a team new to Scala. In practice **many teams have moved back to concrete `IO`/`ZIO`**
for application code and reserve tagless final for libraries — ZIO's ecosystem in particular
argues against it. Being able to say "I know what it is, here's when it's worth it, and it's
often not" is a much stronger answer than enthusiasm.
</details>

### 17. Explain SOLID with an example from your own work.

<details><summary>Answer</summary>

The principles, each in one line plus the smell it prevents:

- **S — Single Responsibility.** One reason to change. *Smell:* a class named `...Manager` or
  `...Util` that imports both a DB driver and an HTTP client.
- **O — Open/Closed.** Extend behaviour without modifying existing code. *In Scala:* add a new
  `case class` to a `sealed trait`, or a new type class instance. (Note the tension with
  exhaustive matching — a sealed ADT is deliberately *closed*, which trades openness for the
  compiler telling you every site that needs updating. Naming that tension is a good sign.)
- **L — Liskov Substitution.** A subtype must honour the supertype's contract — no
  strengthened preconditions, no weakened postconditions. *Smell:* a subclass that throws
  `UnsupportedOperationException`, or `if (x instanceof Y)` in the caller.
- **I — Interface Segregation.** Many small interfaces beat one fat one. *Smell:* implementers
  stubbing out half the methods.
- **D — Dependency Inversion.** Depend on abstractions, not concretions, and the abstraction
  belongs to the *consumer*. *This is the one with the most practical payoff* — it's why
  constructor injection against an interface you own makes code testable (quiz 10 Q1/Q4).

**Give a real example, not a `Shape`/`Circle` one.** From your material, the strongest is the
enriched-endpoint design (quiz 10 Q1):

> The service needed data from our database enriched from another team's HTTP service. I
> defined **my own** `ReferenceDataClient` interface and put their Feign client behind it —
> that's **dependency inversion**: the service depends on an abstraction I own, not on their
> API. It meant their DTOs and failure modes stayed at the boundary, I could unit-test the
> service with a stub and no Spring context, and when we needed to swap the transport the
> business logic didn't change. It's also **single responsibility** — the client adapter
> handles retries, timeouts and their error shape; the service handles the enrichment rule.

**Then the mature caveat**, which is what separates a senior answer:
> SOLID is a set of heuristics for managing change, not laws. Applied mechanically you get
> an interface per class and a factory per interface, which is worse than the problem. I
> apply them where I expect change, and the one I'd never compromise is dependency inversion,
> because it's what makes things testable.

**Worth adding for a Scala role:** several SOLID principles are less pressing in FP because
the units are smaller. A function has single responsibility by default; open/closed is a type
class instance; dependency inversion is a function parameter. **Many patterns and principles
are workarounds for the coarseness of classes** — same observation as quiz 09 Q8.
</details>

### 18. Immutability — make the argument.

<details><summary>Answer</summary>

Four arguments, in order of how much they matter:

1. **Thread safety for free.** An immutable object needs no synchronisation, no locks, no
   defensive copying, and can be shared freely. In the JMM, `final` fields get **freeze
   semantics** so a correctly-constructed instance is safely publishable (quiz 01 Q25).
   **This is the biggest one**, and it's why the Java→Scala migration's real concurrency win
   isn't a library — it's that the default flipped from "thread-safety is opt-in" to
   "mutation is opt-in" (quiz 07 Q11).
2. **Local reasoning.** A value can't change under you, so you can reason about a function
   from its signature and body without tracing every alias. This is what makes refactoring
   safe.
3. **Safe as a map key and in a set.** A mutated key becomes **unreachable and unremovable** —
   demonstrated in `P11Collections.java` Case C (get returns null, remove returns null, and
   iteration still shows the entry).
4. **It's the foundation of event sourcing.** An immutable, append-only event log *is* the
   idea (quiz 13). You get a full audit trail, time travel, and replayability — which for a
   regulated post-trade system isn't a nice-to-have, it's the requirement.

**The costs, stated honestly** — an answer that only lists benefits sounds naive:
- **Allocation.** Every "update" allocates. `case class copy`, persistent-collection path
  copying (`Map + (k -> v)` copies O(log₃₂ n) nodes), boxed elements. Measured in
  `S03AllocationPressure.scala`: a `List[Int]` of 1 M costs ~38 MB vs 3.8 MB for
  `Array[Int]`.
- **But** — most of that garbage **dies in eden**, and a copying collector reclaims it for
  almost nothing. The cost is GC *frequency*, not per-object overhead, and it only matters in
  a genuinely hot loop (quiz 06 D3).
- **Structural sharing** makes persistent collections far cheaper than naive copying —
  a `Vector` update shares almost everything.
- Where it genuinely doesn't pay: tight numeric loops. Use `Array` and a `while` loop there
  and confine the mutation (measured: 0 MB allocated, ~90× faster than the `List` pipeline).

**The line to land:** *"I default to immutable and treat mutation as a local optimisation I
have to justify — and I measure before I introduce it, because in the 99% of code that runs
once per request it buys nothing and costs clarity."*
</details>

### 19. Scala 2 vs Scala 3 — what changed that matters?

<details><summary>Answer</summary>

Worth knowing which the team is on — ask. The pack's local toolchain is **2.13.15**, and
2.13 is the migration bridge (3.x is source- and mostly binary-compatible with 2.13 via
TASTy).

**The changes that matter in practice:**
- **Implicits were split into distinct features**, because the overloading was recognised as a
  design mistake (Q9): `given`/`using` for instances and parameters, `extension` for methods,
  and an explicit `Conversion` type class for conversions.
- **Optional braces / significant indentation** — cosmetic but pervasive; both styles compile.
- **`enum`** — proper enums, and concise ADT syntax:
  ```scala
  enum TradeEvent:
    case Executed(id: String, qty: Int)
    case Cancelled(id: String, reason: String)
  ```
- **Union and intersection types** — `String | Int`, `Reader & Writer`.
- **`opaque type`** — a zero-overhead type alias. **This replaces value classes and fixes
  their biggest flaw**: a `AnyVal` value class silently *boxes* when used generically, in an
  array, or in an `Option`, whereas an opaque type compiles to the underlying type with no
  boxing surprises (quiz 06 D1). Genuinely useful for domain primitives — `TradeId`,
  `Quantity` — which is exactly what a post-trade domain model wants.
- **Trait parameters** — traits can take constructor params.
- **`export` clauses**, better type inference, match types, improved exhaustivity checking.
- **Macros were completely redesigned** — the main source of migration pain, since Scala 2
  macro-heavy libraries needed rewrites.
- **Explicit nulls** (`-Yexplicit-nulls`) — makes reference types non-nullable by default.

**The honest note:** ecosystem adoption took years but is now broadly there (Cats, ZIO,
http4s, doobie, Pekko all support 3). Current stable versions as of Aug 2026: **Cats Effect
3.7.0**, **ZIO 2.1.26**, **Pekko 1.6.x**. Plenty of production systems remain on 2.13, and in
banking that's the norm. **"Which version are you on, and are you planning to move?"** is a
good question to ask them — it tells you a lot about the codebase's age and the team's
appetite for change.
</details>

### 20. Sketch a domain model for a trade using Scala's type system.

<details><summary>Answer</summary>

A synthesis question — this is where a Scala interview for a post-trade team is likely to go,
and it lets you demonstrate ADTs, smart constructors, and `Either` together.

```scala
// --- Domain primitives: no bare String/Int in the model ---
opaque type TradeId  = String                    // Scala 3; a value class in 2.x
opaque type Quantity = Long
final case class Money(minor: Long, ccy: Currency)   // never Double for money

// --- Closed set of states: sealed => exhaustive matching ---
sealed trait TradeState
object TradeState {
  case object New                                  extends TradeState
  case object Confirmed                            extends TradeState
  final case class Cleared(ccp: Ccp)               extends TradeState
  final case class Settled(on: LocalDate)          extends TradeState
  final case class Failed(reason: FailureReason)   extends TradeState
}

// --- Events: immutable, append-only (quiz 13) ---
sealed trait TradeEvent { def tradeId: TradeId; def occurredAt: Instant }
object TradeEvent {
  final case class Executed(tradeId: TradeId, qty: Quantity, price: Money, occurredAt: Instant) extends TradeEvent
  final case class Confirmed(tradeId: TradeId, occurredAt: Instant)                             extends TradeEvent
  final case class Cleared(tradeId: TradeId, ccp: Ccp, occurredAt: Instant)                     extends TradeEvent
  final case class Settled(tradeId: TradeId, on: LocalDate, occurredAt: Instant)                extends TradeEvent
}

// --- Typed errors, not exceptions ---
sealed trait TradeError
object TradeError {
  final case class InvalidTransition(from: TradeState, event: TradeEvent) extends TradeError
  final case class UnknownTrade(id: TradeId)                             extends TradeError
}

// --- A pure, total state machine: (state, event) => Either[error, state] ---
def apply(state: TradeState, event: TradeEvent): Either[TradeError, TradeState] =
  (state, event) match {
    case (TradeState.New, _: TradeEvent.Confirmed)       => Right(TradeState.Confirmed)
    case (TradeState.Confirmed, e: TradeEvent.Cleared)   => Right(TradeState.Cleared(e.ccp))
    case (TradeState.Cleared(_), e: TradeEvent.Settled)  => Right(TradeState.Settled(e.on))
    case (s, e)                                          => Left(TradeError.InvalidTransition(s, e))
  }
```

**The points to make while sketching:**
1. **`sealed` gives exhaustivity** — add a `Netted` event and the compiler flags every match
   that needs updating. In a regulated domain where the event set grows, that's the feature.
2. **Make illegal states unrepresentable.** `Cleared` *requires* a CCP; `Settled` *requires* a
   date. You can't construct a settled trade with no settlement date, so a whole class of
   validation disappears.
3. **Wrap primitives.** `opaque type TradeId` means you can't pass an account id where a trade
   id belongs — a bug that a `String`-typed model can't catch and that costs real money here.
4. **`Money` as minor units in a `case class`, never `Double`.** Floating point for money is a
   correctness bug; and never a bare `Long` without a currency.
5. **The transition function is pure and total** — `(state, event) => Either[error, state]`.
   That makes it **trivially unit-testable with no mocks**, and it's the same function used
   for replaying history and for handling live events (quiz 13 Q1). It's also exactly the
   shape a Given-When-Then acceptance test wants (quiz 14 Q4).
6. **Events are immutable and past-tense** — `Executed`, not `Execute`. A command is an
   intent that can be rejected; an event is a fact that happened (quiz 13 Q2).

This one sketch demonstrates ADTs, sealed traits, pattern matching, smart constructors,
typed errors, immutability, and event sourcing. **If you get an open "model this domain"
question, this is the answer.**
</details>
